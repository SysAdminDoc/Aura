# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 9
**Date:** 2026-06-04
**Repo state:** `main`, `1b0970c`, `versionCode 112`

## Executive Summary

Cycle 9 focused on Firebase/community backend operations: Realtime Database rules, Cloud Storage rules, App Check, abuse throttling, public upload lifecycle, and moderation/report workflows. Aura has made meaningful progress with server-side Custom Claims for admin moderation, but the operational surface is not yet release-ready for public uploads at scale.

Top findings:

- P0: Aura has a tracked `database.rules.json`, but no tracked `firebase.json`, `.firebaserc`, `storage.rules`, Firebase Emulator Suite config, or rules-unit test harness. Rules correctness is currently hard to verify before deploy.
- P0: Community upload ownership is inconsistent: RTDB rules authorize updates against `uploaderUid`, while sound and wallpaper upload repositories write `uploaderId`. That blocks or weakens future owner edit/delete flows unless normalized.
- P1: Firebase Storage uploads are only constrained by client-side validation in the app. No version-controlled Storage rules currently enforce path ownership, max file size, or content type.
- P1: Anonymous Auth plus vote markers reduce casual abuse, but they do not prove requests come from Aura. App Check enforcement, quotas, and abuse throttles need a staged rollout plan.
- P1: The moderation state is a boolean hide flag and there is no visible report queue with reason, reporter, status, resolver, audit timestamp, or user-block story.
- P2: Backend operations still need a release runbook: deploy/rollback steps, emulator coverage, App Check monitor-then-enforce gates, orphaned Storage cleanup, and community data retention/deletion evidence.

## Current State

Local evidence reviewed:

- `database.rules.json` is the only tracked Firebase rules/config file found in the repo. It gates admin moderation with `auth.token.admin === true`, auth-gates community writes, exposes public reads for votes, moderation state, community sounds, community wallpapers, creator profiles, and collection shares, and validates selected fields such as names, categories, and tags.
- No tracked `storage.rules`, `firebase.json`, or `.firebaserc` file was found. No Firebase rules test harness, `@firebase/rules-unit-testing`, Firebase Emulator Suite config, or rules CI job surfaced in tracked files.
- `docs/firebase-admin-claims.md` documents Custom Claims and says RTDB rules are not deployed automatically. It includes manual deploy guidance, but there is no config-backed deploy target in the repo.
- `FreeVibeApp.kt` signs in the community identity at startup and refreshes admin Custom Claims through `VoteRepository.refreshAdminFromClaims()`. No App Check initialization or enforcement doc was found in the app code search.
- `UploadRepository.kt` uploads sounds to Firebase Storage under `sounds/{uploaderId}/...`, validates file size and MIME type locally, saves public metadata in `community_sounds`, stores `downloadUrl`, `originalFileName`, `uploaderId`, and `uploaderLabel`, and deletes the Storage blob if metadata save fails.
- `WallpaperUploadRepository.kt` uploads wallpapers under `wallpapers/{uploaderId}/...`, validates/decodes/compresses images locally, saves public metadata in `community_wallpapers`, stores public URLs and `originalFileName`, and deletes the Storage blob if metadata save fails.
- `database.rules.json` uses `data.child('uploaderUid').val() === auth.uid` for owner update/delete authorization, while both upload repositories write `uploaderId`. Cycle 4 already identified this as a privacy/lifecycle risk; Cycle 9 confirms it is also a backend authorization risk.
- `VoteRepository.kt` stores votes under `/votes/{contentId}`, mirrors legacy voter markers, treats normal downvotes as local hides, and lets admins write `/moderation/{contentId}=true`. The global moderation value has no reason, timestamp, admin UID, report link, or audit trail.
- `CommunityIdentityProvider.kt` signs in anonymously when Firebase Auth is available and falls back to a local UUID when not. It also includes legacy identity values for migration. That preserves UX but complicates ownership, deletion, and anti-abuse guarantees.
- Search found only `gradle/verification-metadata.xml` references to Firebase App Check artifacts, not an implementation or runbook. This suggests App Check is not yet an operationally enforced control in the tracked source.

External evidence reviewed:

- Firebase Security Rules docs describe Realtime Database `.read`, `.write`, `.validate`, and `.indexOn` rules, and emphasize that validation rules define correct data shape and do not cascade.
- Firebase Custom Claims docs use `auth.token.admin === true` as the canonical server-side authorization pattern for admin-style access.
- Firebase Emulator Suite docs support local rules development and testing for Realtime Database and Cloud Storage, which makes a rules test harness a practical release gate instead of a manual console-only check.
- Firebase Cloud Storage Security Rules docs expose `request.auth`, `request.resource.size`, and `request.resource.contentType`, making server-side path, size, and MIME constraints possible for Aura's sound and wallpaper uploads.
- Firebase App Check works with Realtime Database and Cloud Storage, and Firebase supports enabling enforcement for standard services after monitoring request metrics.
- Firebase Storage Android docs support explicit `StorageReference.delete()` for uploaded files and note that deletes can fail for permission or missing-file reasons.
- Google Cloud Storage lifecycle management supports automatic delete rules and warns lifecycle changes can take time to propagate. This is useful for orphaned upload cleanup and retention planning, but it is not a substitute for immediate user/admin deletion flows.
- Google Play's UGC policy requires in-app reporting for public UGC and blocking users where public UGC/social interaction applies.

## Findings

### Rules need a test and deploy source of truth

Aura has RTDB rules in source, but the repository does not include the Firebase project/deploy config or emulator tests that would prove the rules before production changes. The current `docs/firebase-admin-claims.md` manual deploy guidance is useful, but it is not enough for a public community surface where one bad rule can expose writes, block owners, or disable moderation.

Planning implication: add a Firebase rules harness that loads `database.rules.json`, adds tracked Storage rules, runs emulator-backed tests for anonymous/auth/admin personas, and documents deploy/rollback steps before any community launch or rule change.

### Storage is missing server-side invariants

Sound and wallpaper uploads have good client validation, but client validation is not an enforcement layer. Storage rules should enforce that authenticated users can only write under their own path, cap audio/image sizes, restrict content types, and define whether reads are public or mediated through public download URLs.

Planning implication: create `storage.rules` and tests that cover sounds and wallpapers separately. Keep app-side validation for UX, but treat Storage rules as the production guardrail.

### Owner field mismatch blocks deletion and lifecycle promises

The upload repositories write `uploaderId`, while rules check `uploaderUid`. That mismatch means future owner edits/deletes will not pass the intended rule unless data is migrated or rules support both names. It also makes privacy/delete promises risky because the backend cannot consistently prove owner authority from the current metadata.

Planning implication: normalize community metadata around one owner field, migrate existing metadata, and add delete/takedown tests that delete RTDB metadata and Storage blobs together.

### App Check and quotas need staged enforcement

Anonymous Auth identifies a user record, but it does not prove calls come from Aura or prevent scripted clients from creating many accounts. Vote markers limit one upvote per identity, but uploads, reports, and profile writes still need per-UID/IP-like quota design. Firebase App Check can protect RTDB and Storage requests, but it should be monitored before enforcement to avoid locking out non-Play or debug installs.

Planning implication: introduce App Check with Play Integrity and debug-provider runbooks, monitor request metrics, then enforce for RTDB/Storage. Pair it with per-UID counters or Cloud Functions-backed quotas for uploads, votes, reports, and follow actions.

### Moderation needs an auditable report queue

Aura currently has a global hidden set, but not a moderation workflow. Public UGC needs report categories, reporter privacy, status transitions, resolver identity, timestamps, reasons, and user-facing outcomes. The current boolean hide flag cannot answer who hid content, why it was hidden, whether it came from a report, or when it can be restored.

Planning implication: build a typed `/reports` or `/moderation_cases` model with Custom Claim admin resolution, report spam controls, user-block hooks where applicable, and rules tests for reporter/admin/public access boundaries.

### Backend operations need release evidence

The backend is part of the release artifact even though it is not compiled into the APK. Aura needs evidence that the deployed backend matches the repo, App Check enforcement was staged, rules tests passed, orphaned Storage cleanup exists, and data deletion/takedown flows were exercised.

Planning implication: add a community backend runbook and release checklist rows for rule test reports, deploy target, rollback target, App Check status, Storage lifecycle policy, moderation queue status, and deletion evidence.

## Roadmap Queue

- [ ] P0 - Firebase rules test and deploy harness
  - Why: Aura has tracked RTDB rules but no tracked Firebase deploy config, Storage rules file, emulator config, or rules test harness.
  - Evidence: `database.rules.json`; missing `firebase.json`, `.firebaserc`, `storage.rules`, and rules-unit test files; Firebase Emulator Suite docs; Firebase RTDB/Storage rules docs.
  - Touches: `firebase.json`, `.firebaserc` or documented project alias policy, `database.rules.json`, new `storage.rules`, rules tests, CI/release checklist, `docs/firebase-admin-claims.md`.
  - Acceptance: emulator-backed tests cover public read, authenticated write, owner update/delete, admin moderation, votes/voters, reports, creator profiles, and collection shares; deploy and rollback commands are documented; CI or a release preflight runs the rules suite.
  - Verify: rules tests fail on unauthenticated writes and non-owner updates; admin Custom Claim tests pass; `firebase emulators:exec` or equivalent command exits cleanly before deploy.

- [ ] P0 - Community owner field normalization and delete/takedown flow
  - Why: RTDB rules authorize owners through `uploaderUid`, while upload repositories write `uploaderId`; Aura cannot safely promise self-service delete/edit or owner-only metadata writes until this is consistent.
  - Evidence: `database.rules.json`; `UploadRepository.kt`; `WallpaperUploadRepository.kt`; Cycle 4 community data lifecycle finding; Firebase Storage delete docs.
  - Touches: upload metadata schema, migration/backfill plan, RTDB rules, Storage delete path, upload detail actions, privacy/community-data docs.
  - Acceptance: one canonical owner field is used for sounds and wallpapers; existing metadata is migrated or dual-read safely; owners can delete their metadata and Storage object; admins can takedown content; failed blob/metadata deletes leave auditable retry state.
  - Verify: owner delete removes feed item and Storage object; non-owner delete fails in rules tests; admin takedown hides/removes as designed; orphan retry path is exercised.

- [ ] P1 - Storage rules and orphan lifecycle cleanup
  - Why: Upload size/type/path checks currently live in app code, but Storage needs server-side enforcement and cleanup for orphaned blobs or removed content.
  - Evidence: no tracked `storage.rules`; sound uploads allow 20 MB locally; wallpaper uploads compress to 4 MB locally; Firebase Storage rules docs expose `request.resource.size` and `request.resource.contentType`; Cloud Storage lifecycle docs.
  - Touches: `storage.rules`, Storage emulator tests, upload repositories, cleanup job/runbook, lifecycle policy docs, release checklist.
  - Acceptance: Storage rules restrict writes to authenticated owner paths, enforce sound/image MIME and size ceilings, define read behavior, and block cross-user overwrite/delete; lifecycle or cleanup process handles abandoned temp/orphan objects without deleting valid public uploads.
  - Verify: emulator tests reject oversize/wrong-type/cross-owner uploads; metadata-save failure cleanup still works; orphan cleanup dry run reports expected objects before delete.

- [ ] P1 - App Check and community abuse throttling
  - Why: Anonymous Auth and vote markers do not prove requests come from Aura or prevent scripted uploads, votes, reports, follows, and profile writes at scale.
  - Evidence: `CommunityIdentityProvider.ensureSignedIn()` anonymous/fallback identity; `VoteRepository.upvote()` voter marker; no App Check init/runbook found; Firebase App Check docs for RTDB and Storage.
  - Touches: App Check initialization, debug-provider docs, Firebase console enforcement runbook, upload/vote/report quota design, backend counters or Cloud Functions if needed, release checklist.
  - Acceptance: App Check is installed with Play Integrity plus debug/dev instructions; request metrics are monitored before enforcement; RTDB and Storage enforcement dates are recorded; abuse quotas exist for uploads, reports, votes, follows, and profile edits.
  - Verify: debug build works with debug token; release build obtains valid token; monitor-mode metrics are reviewed; after enforcement, unauthenticated/unverified scripted requests fail while normal app flows pass.

- [ ] P1 - Moderation report queue and audit trail
  - Why: The current `/moderation/{contentId}=true` boolean hides content but does not capture report reason, reporter privacy, resolver, timestamp, status, appeal/restore, or block semantics required for public UGC operations.
  - Evidence: `VoteRepository.moderateHide()` and `moderateUnhide()`; `database.rules.json` moderation path; Cycle 1 report queue item; Cycle 8 Play UGC policy review.
  - Touches: report models/repository, report actions in content detail screens, RTDB rules, admin moderation UI, privacy/report docs, Play app-content packet.
  - Acceptance: users can report community content with categories; reports are App-Checked/authenticated and rate-limited; admins can resolve/hide/unhide with reason and timestamp; audit entries record resolver UID without exposing reporter identity publicly; block-user behavior is defined or explicitly out of scope.
  - Verify: report create/read/admin-resolve rules tests; manual report -> admin hide -> feed removal -> unhide flow; reporter data is not public; Play UGC checklist row is complete.

- [ ] P2 - Community backend operations runbook
  - Why: Community backend changes can break public reads/writes independently from APK builds, and Aura has no single release artifact tying rules, App Check, Storage cleanup, moderation, and deletion evidence together.
  - Evidence: `docs/firebase-admin-claims.md` manual deploy notes; missing Firebase deploy config; Cycle 8 release metadata packet; Firebase and Cloud Storage lifecycle docs.
  - Touches: `docs/community-backend-runbook.md`, release checklist, deploy/rollback notes, incident/takedown notes, App Check enforcement ledger, Storage lifecycle policy evidence.
  - Acceptance: runbook records current deployed rules hash/version, deploy command, rollback command, App Check monitor/enforce status, rules test command, cleanup cadence, takedown SLA, and owner/admin deletion verification steps.
  - Verify: dry-run release checklist includes backend evidence; a simulated bad rules deploy has a rollback path; a sample takedown/delete case leaves documented evidence without leaking user data.

## Open Questions

- Should Aura keep public unauthenticated reads for community feeds, or move to auth/App Check-gated reads once App Check is fully staged?
- Should owner deletion hard-delete public uploads immediately, soft-hide first, or queue deletion for admin/moderation review?
- Should report/moderation data live in Realtime Database, or should Aura add a minimal Cloud Functions layer for rate limits, audit trails, and cleanup?
- How should non-Play distribution interact with App Check Play Integrity defaults, especially GitHub/Obtainium/Izzy installs?
- Should public download URLs remain in RTDB metadata, or should the app rely on Storage path plus rules and generated URLs where possible?
