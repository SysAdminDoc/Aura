# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 2
**Date:** 2026-06-04
**Repo state:** `main`, `d9c5ba2`, `v6.31.1`, `versionCode 112`

## Executive Summary

Cycle 2 focused on release integrity, FOSS distribution feasibility, and supply-chain verification. Cycle 1 added backend trust and performance items; this pass found a more immediate distribution mismatch: `.github/workflows/release.yml` is tag-triggered but builds `assembleDebug` and uploads the first APK under `app/build/outputs/apk/debug`. That is not aligned with the roadmap's signed-release story, Android's release-build guidance, or non-Play installer expectations.

The next planning additions should be treated as release blockers before any wider GitHub/Obtainium/F-Droid push:

- P0: release workflow must publish signed, non-debuggable release APKs, not debug APKs.
- P0: F-Droid/Izzy strategy needs an explicit full-vs-foss flavor decision because the current build has Firebase, Google Services, Play Services ML Kit, and no product flavors.
- P1: add Gradle dependency verification, Dependency Review, OpenSSF Scorecard, artifact attestations, and checksums to the release/supply-chain path.
- P1: add privacy-preserving crash/ANR evidence collection that fits the no-tracking charter and works outside Play.

## Evidence Reviewed

Local evidence:

- `git pull --rebase` returned "Already up to date"; only untracked `AGENTS.md` remained after Cycle 1 push.
- `.github/workflows/release.yml` is triggered by `v*` tags or manual dispatch, runs `./gradlew assembleDebug`, searches `app/build/outputs/apk/debug`, and uploads that APK through `softprops/action-gh-release@v2`.
- `.github/workflows/verify.yml` runs assembleDebug, unit tests, and lint on push/PR, but does not run release assembly, dependency review, dependency submission, artifact attestation, or checksumming.
- `app/build.gradle.kts` applies `com.google.gms.google-services` and depends on Firebase Auth/Database/Storage, `play-services-mlkit-subject-segmentation`, and `play-services-base`.
- `app/build.gradle.kts` has build types and source sets, but no product flavors or foss/full source-set split.
- Source search found no `gradle/verification-metadata.xml`, dependency locking, CycloneDX/SBOM generation, GitHub artifact attestation, OpenSSF Scorecard workflow, or Dependency Review action.
- `FreeVibeApp.kt` writes a local `crash.log`; no Crashlytics/Sentry dependency was found. That is aligned with the no-tracking charter but needs user-visible diagnostics/export if releases are outside Play.

External sources:

- Android command-line release docs say release builds should be signed with the appropriate signing key; Android build/run docs distinguish debug builds intended for development from release variants.
- Android `apksigner` docs describe signing and verifying APK signatures across supported platform versions.
- F-Droid Inclusion Policy and FAQ state F-Droid cannot build apps using proprietary tracking/analytics dependencies and generally cannot use Google repository proprietary libraries such as Firebase/Play Services.
- F-Droid reproducible-build docs describe binary reproducibility, upstream signature copying, and environmental differences that can break APK reproducibility.
- Gradle dependency verification docs record expected dependency/plugin checksums in `gradle/verification-metadata.xml`.
- GitHub artifact attestation docs describe build provenance for workflow artifacts; GitHub Dependency Review action docs cover PR dependency/license review; OpenSSF Scorecard provides open-source security health checks.
- Android vitals docs focus on crash/ANR/partial-wake-lock metrics, but those are Play Console centric and need a non-Play fallback for Aura's current distribution path.

## Findings

### Release workflow uploads debug APKs

- Problem: tag releases appear to ship a debug build. Debug APKs are meant for development and are not the right trust boundary for GitHub/Obtainium users.
- Evidence: `.github/workflows/release.yml` runs `./gradlew assembleDebug` and finds APKs under `app/build/outputs/apk/debug`.
- Impact: debug builds can have different optimization, debuggability, signing, and security posture than release builds. The roadmap says signed GitHub releases, but the workflow does not prove that.
- Planning action: add a P0 release item requiring signed release assembly, `apksigner verify --print-certs`, SHA-256 checksum publication, artifact attestation, and a guard that fails if the uploaded APK is debuggable.

### F-Droid strategy conflicts with current dependency shape

- Problem: Aura wants F-Droid/Izzy distribution, but the current app has Firebase, Google Services plugin, Play Services ML Kit, and no product flavor boundary.
- Evidence: `app/build.gradle.kts` includes Firebase BoM/Auth/Database/Storage, `com.google.gms.google-services`, `play-services-mlkit-subject-segmentation`, and `play-services-base`; no `productFlavors` were found.
- Impact: F-Droid mainline may be blocked unless Aura creates a FOSS flavor, removes/replaces proprietary dependencies for that flavor, or explicitly chooses Izzy/GitHub/Obtainium for full-feature distribution only.
- Planning action: add a P0 distribution decision item that defines `full` and `foss` feature matrices before opening an F-Droid metadata PR.

### Supply-chain controls are missing from CI/release

- Problem: there is no dependency checksum metadata, no dependency review, no Scorecard workflow, no artifact attestation, no checksums, and no SBOM/provenance publication.
- Evidence: source search found no `verification-metadata.xml`, dependency-locking metadata, CycloneDX/SBOM, Scorecard workflow, or artifact attestation workflow.
- Impact: this is a gap for a side-loaded personalization app that asks users to trust GitHub releases and will eventually ingest binaries with youtubedl/FFmpeg/native components.
- Planning action: add a P1 hardening item that starts with Gradle dependency verification and GitHub release attestations/checksums, then layers Dependency Review/Scorecard/SBOM.

### Crash evidence is local-only

- Problem: Aura avoids third-party crash analytics, which fits the charter, but non-Play distribution means maintainers may not see crash/ANR clusters unless users can export useful diagnostics.
- Evidence: `FreeVibeApp.kt` installs an uncaught-exception handler and appends to `filesDir/crash.log`; there is no Crashlytics/Sentry dependency, and Android vitals is Play Console centric.
- Impact: Android 8-12 crash fixes are harder to validate across GitHub/Obtainium users without an opt-in diagnostic bundle.
- Planning action: add a P1 diagnostics item for user-controlled crash log export, environment/version metadata, ANR hints, and a "copy issue bundle" path with no automatic upload.

## Prioritized Roadmap Additions

- [ ] P0 - Release workflow publishes signed release APKs
  - Why: tag releases must not publish debug APKs to GitHub/Obtainium users.
  - Evidence: `.github/workflows/release.yml` currently runs `assembleDebug` and uploads from `app/build/outputs/apk/debug`.
  - Touches: NX-8 release workflow and distribution docs.
  - Acceptance: tag workflow builds signed release/universal plus split APKs, verifies signatures, fails on debuggable APKs, publishes SHA-256 checksums, and records versionCode/versionName.
  - Verify: `git tag v*` dry run, `apksigner verify --print-certs`, checksum comparison, install/update from Obtainium.

- [ ] P0 - Full-vs-foss distribution flavor decision
  - Why: F-Droid mainline eligibility is not credible until Firebase/Play Services dependencies are isolated or explicitly excluded from a FOSS flavor.
  - Evidence: `app/build.gradle.kts` has Firebase/Google Services/Play Services dependencies and no product flavors.
  - Touches: NX-8, N-2, N-3, App Check item from Cycle 1.
  - Acceptance: documented matrix for GitHub/Obtainium/Izzy/F-Droid; `full` build keeps Firebase/community/App Check; `foss` build either disables those surfaces or uses acceptable substitutes; CI proves both selected variants.
  - Verify: `assembleFullRelease`, `assembleFossRelease`, dependency tree review for FOSS flavor, F-Droid metadata preflight.

- [ ] P1 - Supply-chain verification lane
  - Why: side-loaded APKs need stronger provenance than a release asset link.
  - Evidence: no Gradle dependency verification metadata, no Dependency Review, no Scorecard, no attestations, no SBOM/checksum publication found.
  - Touches: NX-8, NX-12, N-1.
  - Acceptance: Gradle dependency verification metadata committed; Dependency Review and Scorecard run on PRs; release artifacts have SHA-256 files and GitHub artifact attestations; SBOM plan documented even if deferred.
  - Verify: PR with dependency change triggers review; Gradle build fails on checksum drift; GitHub release shows checksums and attestations.

- [ ] P1 - Opt-in crash/ANR diagnostics bundle
  - Why: no-tracking releases still need actionable crash evidence from GitHub/Obtainium/F-Droid users.
  - Evidence: `FreeVibeApp.kt` writes `crash.log`; no Crashlytics/Sentry dependency was found; Android vitals is Play/console oriented.
  - Touches: Settings diagnostics, support docs, release issue template.
  - Acceptance: Settings exposes last crash timestamp and "copy/export diagnostics"; bundle includes app version, Android version, ABI, active source/provider, sanitized crash log tail, and reproduction fields; nothing uploads automatically.
  - Verify: synthetic crash writes log, export redacts paths/tokens, issue template accepts bundle, no network call occurs.

## Non-goals

- No implementation changes in this research pass.
- No change to signing keys, workflows, Gradle files, source code, tests, or Firebase configuration.
- No recommendation to add automatic telemetry or ad/analytics SDKs.

## Open Questions

- Should Aura pursue true F-Droid mainline eligibility, or treat IzzyOnDroid/GitHub/Obtainium as the primary non-Play path because community features depend on Firebase and App Check?
- Does the owner have release signing material available to GitHub Actions, or should signed releases remain local until a secure CI signing story exists?
- Should the future `foss` flavor drop community uploads entirely or replace Firebase with a self-hostable backend contract?
- Should crash diagnostics be exposed only in Settings or also after restart when a previous crash log exists?
