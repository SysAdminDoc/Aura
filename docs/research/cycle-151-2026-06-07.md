# Cycle 151 - Rotation trigger boot permission decision

Date: 2026-06-07

## Question

Cycle 14 left an open decision for `android.permission.RECEIVE_BOOT_COMPLETED`.
Aura declared the permission, but the app did not register a boot receiver.
Rotation triggers use dynamic unlock and screen-off receivers while
`RotationTriggerService` is running, so the release policy needed one explicit
behavior:

- remove the permission and document that rotation triggers resume after
  opening Aura, or
- add a boot receiver that restarts the service only for opted-in users with
  foreground-service policy evidence.

## Local findings

- `app/src/main/AndroidManifest.xml` declared
  `android.permission.RECEIVE_BOOT_COMPLETED` before this cycle.
- Source search found no `Intent.ACTION_BOOT_COMPLETED`,
  `Intent.ACTION_LOCKED_BOOT_COMPLETED`,
  `android.intent.action.BOOT_COMPLETED`, or
  `android.intent.action.LOCKED_BOOT_COMPLETED` app source terms.
- `RotationTriggerService` dynamically registers unlock and screen-off
  receivers while the foreground service is alive.
- `FreeVibeApp` reconciles rotation trigger state on app cold start, so the
  honest current behavior is that trigger listeners resume after opening Aura.

## Source-backed decision

The current implementation does not need the boot-completed permission because
there is no boot receiver. Keeping the permission would make the manifest,
privacy ledger, alternative-store disclosure, and release QA imply a behavior
Aura does not currently implement.

The safer Cycle 151 decision is:

- remove `android.permission.RECEIVE_BOOT_COMPLETED` from the manifest;
- remove the permission from Data safety and alternative-store permission
  disclosures;
- document the user-visible behavior in
  `docs/rotation-trigger-boot-behavior.md`;
- add `tools/rotation_boot_permission_check.py` so release gates fail if the
  permission or boot receiver terms return without updating the packet.

If Aura later needs boot restoration for opted-in rotation triggers, that should
be a dedicated feature with a receiver, service startup policy, notification
copy, foreground-service declaration evidence, and updated store/privacy
disclosures in the same change.

## Implementation

- Removed `android.permission.RECEIVE_BOOT_COMPLETED` from the manifest.
- Updated privacy Data safety and alternative-store disclosure packets to match
  the 14-permission manifest.
- Added `docs/rotation-trigger-boot-behavior.md` and
  `docs/rotation-trigger-boot-behavior.json`.
- Added `tools/rotation_boot_permission_check.py` and focused unit tests.
- Wired verify and release workflows, release metadata consistency, release
  signing, release dry-run, GitHub workflow policy, and supply-chain docs to run
  the new gate.
