# Cycle 96 - Creator Follow Callable Handler

## Goal

Implement the next handler-backed callable write surface while fixing the
follow dedupe contract so follow and unfollow retries cannot block each other.

## Research

- `CreatorProfileRepository.followCreator()` currently writes
  `/creator_follows/{uid}/{creatorId}` with `creatorId`, `label`, and
  `followedAt` values after sanitizing the path key.
- `CreatorProfileRepository.unfollowCreator()` removes the same row.
- The Cycle 91 callable contract named `setCreatorFollow`, but its original
  `creatorId` dedupe key was too broad for a setter because an active follow
  dedupe marker could make an immediate unfollow look like a duplicate.
- The callable remains a staged backend implementation; Android still writes
  follows directly until a later repository migration adds the Functions client
  adapter.

## Implementation

- Refined the follows quota contract from `creatorId` to
  `creatorId + desired state` in the Android policy table, backend JSON
  manifest, Functions contract mirror, validator expectations, and quota
  runbook.
- Added `functions/src/followHandler.ts`.
- Switched `setCreatorFollow` from the fail-closed scaffold to
  `createSetCreatorFollowCallable()`.
- The handler now:
  - requires Firebase Auth and App Check through the shared identity guard;
  - rejects client-supplied follower UID overrides;
  - validates the common envelope (`operationId`, `clientSentAt`, `payload`);
  - normalizes `creatorId`, Firebase path key, label, and desired follow state;
  - returns duplicate no-op results before quota reservation when the current
    follow state already matches the requested state;
  - uses action-specific dedupe keys for follow and unfollow requests;
  - reserves UTC quota through the shared quota engine; and
  - sets or removes the final follow row plus a server-owned dedupe marker.
- Added `functions/test/setCreatorFollow.test.cjs` for accepted follow,
  accepted unfollow, no-op duplicates, same-state dedupe, cooldown,
  daily-limit, unauthenticated, missing-App-Check, and invalid payload paths.
- Refreshed `docs/community-backend-manifest.json` and updated callable,
  quota, backend runbook, roadmap, changelog, completed log, and loop state
  docs.

## Remaining Risk

The follow handler has focused Functions unit coverage, not a live Emulator
Suite callable invocation through the Firebase protocol. Android still writes
follow rows directly to RTDB, and production reliance still needs emulator
coverage, Android callable migration, owner-approved deploy evidence, Firebase
Console App Check evidence, and direct RTDB rule tightening.
