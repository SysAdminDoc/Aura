# Cycle 122 Research - GitHub Workflow Permissions Guard

## Goal

Make every GitHub workflow event and permission grant reviewable and
machine-checked so a future workflow edit cannot silently add broader triggers,
extra jobs, or write permissions.

## Local Evidence

- Cycle 117 added snippet checks for Dependency Review, OpenSSF Scorecard, and
  Release, focused on specific security controls.
- Cycle 121 added an allowlist for workflow `uses:` references across all five
  workflow files.
- The remaining workflow posture gap was event and permission drift across the
  full workflow set, including `verify.yml` and `performance.yml`.

## Implementation

- Added `docs/distribution/github-workflow-permissions.json` with the required
  workflow files, allowed events, workflow-level permissions, job-level
  permissions, and expected job IDs.
- Added `tools/github_workflow_permissions_check.py` to reject missing or
  unexpected workflow files, unreviewed workflow events, scalar permission
  declarations such as `write-all`, workflow/job permission drift, missing jobs,
  and unexpected jobs.
- Added `test/tools/github_workflow_permissions_check_test.py` coverage for the
  live workflow set and drift cases around unreviewed events, job permission
  escalation, missing expected job permissions, unexpected jobs, and scalar
  permission declarations.
- Wired `.github/workflows/verify.yml` so the permissions policy check runs
  before Android setup.
- Updated `docs/distribution/supply-chain.md`, `ROADMAP.md`, `COMPLETED.md`,
  `CHANGELOG.md`, and loop state with the new guard.

## Remaining Risk

- The guard is a repository-specific YAML subset parser, not a general GitHub
  Actions interpreter. Keep workflow event and permission declarations in the
  simple map form this policy checks.
- Production community callable enforcement and live GitHub repository security
  claims still require owner-provided evidence described in the current
  continuation state.
