# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 18
**Date:** 2026-06-06
**Repo state:** `main`, `ec90256`, `versionCode 112`

## Executive Summary

Cycle 18 resumed the Cycle 17 license/compliance thread and narrowed the next implementation slice to generated release-runtime notices, a license/SBOM drift gate, and a native/copyleft packet. The previous pass improved the user-facing Licenses screen and added a code-backed provider disclosure matrix, but release evidence is still manual and incomplete.

Top findings:

- P0: Generated OSS notices should be implemented before the next public release expansion. Aura has manual rows in `LicensesScreen.kt`, but no build task that derives notices from the release runtime classpath, no packaged notice asset, and no CI diff gate.
- P0: A generic SBOM is necessary but insufficient. Google Play services OSS notices, AboutLibraries, Licensee, CycloneDX, and SPDX each cover different parts of the problem; Aura needs a layered release lane instead of relying on one tool.
- P0: The youtubedl-android + FFmpeg path needs an artifact inspection step. `app/build.gradle.kts` ships `io.github.junkfood02.youtubedl-android:library:0.18.1` and `:ffmpeg:0.18.1`; upstream says yt-dlp and Python are bundled in the library, and FFmpeg itself requires exact binary/source correspondence for LGPL/GPL compliance.
- P1: Generated dependency inventory should feed both in-app notices and repository/release artifacts. The release workflow currently publishes APK, SHA256SUMS, apksigner text, aapt badging, and attestation, but not notices, SBOM, dependency inventory, or native source-offer evidence.
- P1: The current `docs/distribution/supply-chain.md` still defers SBOM generation until after the N-1 toolchain upgrade. Cycle 18 finds this should be split: add a low-risk notice/drift lane now, then upgrade the SBOM tooling after N-1 if AGP/Gradle compatibility requires it.

- `docs/distribution/supply-chain.md` documents dependency verification and defers SBOM generation until after N-1. It names Gradle plugins, release dependencies, native/FFmpeg/youtubedl artifacts, APK digest, and signing fingerprint as future SBOM scope.
- `docs/legal/provider-policy.md` explicitly says release-runtime dependency notice generation, native/copyleft packets, and item-level license persistence remain open.
- `AUTONOMOUS-LOOP-STATE.md` names Cycle 17 P0 generated OSS notices as the next cycle.
- `rg` found no project usage of `oss-licenses`, `licensee`, `aboutlibraries`, `cyclonedx`, or generated `third-party-notices` artifacts outside the roadmap/research discussion.

External evidence reviewed:

- Google Play services OSS notices docs state that app developers are responsible for displaying open-source notices and provide `oss-licenses-plugin` plus `play-services-oss-licenses` to collect POM license data and display it through `OssLicensesMenuActivity`. The page was last updated 2026-05-29 and currently documents plugin module `com.google.android.gms:oss-licenses-plugin:0.12.0` and runtime library `com.google.android.gms:play-services-oss-licenses:17.5.1`.
- Google's notice plugin scans Maven POM licenses for direct dependencies at compile time and includes transitive notice text for Google Play services libraries used by the app. This is useful for Google/Firebase/Play-service notices but does not solve non-Maven native payload source-offer evidence.
- AboutLibraries v13 splits the Gradle plugin into a main plugin and an Android plugin. The Android plugin automatically generates library definitions as part of the Android build and includes generated data in Android resources; the main plugin provides manual generation tasks. This fits Aura's Compose-first custom Settings surface better than launching Google's stock activity, but it still requires manual handling for native payloads and content sources.
- CycloneDX Gradle plugin generates JSON/XML SBOMs from direct and transitive resolved dependencies and supports multi-project aggregation. The Gradle Plugin Portal lists `org.cyclonedx.bom` 3.2.4 as current as of 2026-04-08. This is release evidence, not a polished in-app license UI.
- SPDX is an ISO-recognized open standard for SBOM information, including provenance, license, security, and related supply-chain metadata. It is suitable as a release artifact or interchange target, but Aura still needs a user-facing notice surface.
- FFmpeg's legal guidance says FFmpeg is LGPL 2.1-or-later by default, optional GPL-covered parts can make the whole FFmpeg binary GPL, and compliance guidance includes distributing exact corresponding source and build configuration for binaries.
- youtubedl-android's README identifies the project as an Android wrapper for yt-dlp, documents the same `library` and `ffmpeg` artifacts Aura uses, and says yt-dlp executable plus Python are bundled in the library.
- NewPipeExtractor's README identifies it as a streaming-site extraction library, lists YouTube and SoundCloud support, and states GPL-3.0-or-later licensing.

## Findings

### A single notice tool will not cover Aura's release obligations

Google's OSS notices tooling is the fastest path for POM-derived Android dependencies and Google Play services transitive notices. AboutLibraries is the better fit for a custom Compose surface because it can generate resources/metadata for the app to render inside Aura's existing Settings flow. Licensee is useful for policy gating. CycloneDX or SPDX is useful for release artifacts and security/compliance interchange. None of these automatically prove FFmpeg build flags, yt-dlp/Python payload versions, or exact-source correspondence for redistributed native binaries.

Planning implication: implement a layered lane:

1. Generate in-app dependency notices from release runtime dependencies.
2. Generate a machine-readable dependency inventory/SBOM artifact for release uploads.
3. Add a policy gate that fails on unknown or newly introduced licenses until reviewed.
4. Add a separate native/copyleft packet for youtubedl-android, yt-dlp/Python payloads, NewPipeExtractor, and FFmpeg.

### Manual `LicensesScreen.kt` rows should become curated overlays, not the source of truth

The hand-maintained `licenses` list is now a better stopgap, but it can still drift whenever a dependency changes. The most useful retained manual data is not the dependency list itself; it is Aura-specific explanations such as "used for QR code support" or "used for YouTube extraction". Generated inventory should own dependency identity/license/version, while curated overlay metadata can add user-friendly descriptions and risk notes.

Planning implication: create `docs/legal/dependency-notice-overrides.json` or equivalent to augment generated rows with display descriptions, native-payload caveats, provider-disclosure links, and legal-mode disablement notes. Tests should compare direct runtime dependencies to generated/curated rows.

### Release workflow should publish notices with the APK

The release workflow already packages a signed APK, checksum, release notes, apksigner output, aapt badging, and an attestation. That makes it the right insertion point for notice artifacts. Users installing through GitHub/Obtainium should be able to inspect notices without installing the app, and in-app Settings should expose the same data.

Planning implication: extend `.github/workflows/release.yml` with a pre-package notice step that writes artifacts such as:

- `release/THIRD-PARTY-NOTICES.md`
- `release/dependency-license-report.json`
- `release/aura-sbom.cdx.json` or `release/aura.spdx.json`
- `release/native-compliance/youtubedl-android-ffmpeg.md`

Then include those files in `actions/upload-artifact` and tag release uploads.

### Native/copyleft packet must inspect the actual APK/AAR contents

Aura uses reflection to locate FFmpeg from youtubedl-android at runtime. The compliance packet cannot be written only from Gradle coordinates because the shipped APK/AAR payload determines the source-offer and license notice needs. The packet should record package contents, ABI binaries, payload version strings where discoverable, FFmpeg license/build mode, source URLs, and any source archive/link published alongside releases.

Planning implication: add a script or Gradle task that unzips `app-release.apk` plus cached AARs for `io.github.junkfood02.youtubedl-android:library` and `:ffmpeg`, lists native libraries/assets/scripts, and writes a factual inventory. Do not copy private keys or credentials into the report.

### N-1 should not block the first notice gate

`docs/distribution/supply-chain.md` defers SBOM generation until the AGP/Gradle/Kotlin migration, but Cycle 18 found there is a smaller safe slice that can ship on the current toolchain: generate dependency notices/report data and fail CI on drift. The full CycloneDX/SPDX SBOM can remain tied to N-1 if plugin compatibility or dependency resolution cost becomes an issue.

Planning implication: split "Generated OSS notices and license drift gate" into a current-toolchain P0 and "Full SBOM upgrade after N-1" into a follow-up.

## Recommended Roadmap Insertions

1. P0 - Generated release-runtime notice pipeline.
2. P0 - Dependency license drift gate for `releaseRuntimeClasspath`.
3. P0 - Native/copyleft artifact inspection packet for NewPipeExtractor, youtubedl-android, bundled yt-dlp/Python payloads, and FFmpeg.
4. P1 - Release workflow publishes notices/SBOM/native packet next to the APK.
5. P1 - Curated dependency notice overlay that augments generated notices with Aura-specific usage descriptions.
6. P1 - Split current-toolchain notice gate from post-N-1 full SBOM modernization.

## Verification Targets

- A local command generates notice data from the release runtime dependency graph without compiling a full APK.
- Adding a sentinel runtime dependency with an unreviewed license fails the notice/license gate.
- `LicensesScreen.kt` reads generated notice data or links to generated notice UI/artifacts instead of relying only on a hard-coded dependency list.
- Release workflow uploads third-party notice and dependency inventory artifacts alongside APK and `SHA256SUMS.txt`.
- A script inspects youtubedl-android and FFmpeg AAR/APK payloads and writes source/license/build-mode evidence.
- `docs/distribution/supply-chain.md` documents the layered lane: user-facing notices, policy gate, SBOM, and native/copyleft packet.
- Generated artifacts avoid exposing `local.properties`, signing config, API keys, Firebase config secrets, or Gradle cache paths.
