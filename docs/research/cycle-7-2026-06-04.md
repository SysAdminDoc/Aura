# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 7
**Date:** 2026-06-04
**Repo state:** `main`, `276ab3a`, `v6.31.1-13-g276ab3a`, `versionCode 112`

## Executive Summary

Cycle 7 focused on AI generation governance: Stability AI integration, bring-your-own API keys, prompt privacy, user-credit spend, generated-media retention, and Google Play's AI-generated content requirements. Aura already has a functional Stability AI path with prompt length limiting, cancel-on-back, error-code mapping, per-call PNG output, and a 50-file generated-image cap. The missing work is policy and trust infrastructure around that feature.

Top findings:

- P0: Aura needs an AI generation disclosure and consent gate before expanding generation. A prompt is sent to Stability AI, the user's API key and credits are used, and generated prompt fragments are stored locally in favorites/tags if saved.
- P0: Google Play requires apps that generate AI content to include in-app reporting or flagging for offensive generated content. Aura's AI wallpaper screen has no report/flag path today.
- P1: Stability API keys are sanitized and excluded from backup through DataStore rules from prior privacy work, but they are still stored as app preferences and may be seeded from `BuildConfig.STABILITY_AI_KEY`. Release builds need a "no bundled third-party AI key" guard and clearer key storage docs.
- P1: The current UI maps 402/403/429 failures, but it does not provide preflight credit/rate-limit expectations, duplicate prompt safeguards, or a generation ledger. Users can unknowingly spend credits repeatedly.
- P1: Prompt text leaks into local metadata by design: tags are mined from prompt words and favorites use `AI: ${prompt.take(60)}`. That needs a retention/redaction decision and privacy-policy coverage.
- P2: On-device AI remains a future decision gate, not a near-term implementation target. It could reduce third-party data sharing and credit spend, but device support, battery, model size, licensing, and moderation remain unresolved.

## Current State

Local evidence reviewed:

- `app/build.gradle.kts` reads `stability.ai.key` from `local.properties` into `BuildConfig.STABILITY_AI_KEY`; the adjacent comment says API-key defaults are baked in and users can override through Settings.
- `PreferencesManager.kt` exposes `stabilityAiKey` from DataStore and sanitizes API keys by trimming and removing control characters before saving.
- `SettingsScreen.kt` and `AiWallpaperScreen.kt` ask for a Stability AI API key and direct users to `platform.stability.ai`; they do not disclose prompt sharing, credit spend, or generated-content reporting.
- `AiWallpaperViewModel.kt` caps prompts at 500 characters, requires a nonblank API key, cancels any prior generation before starting another, and cancels the in-flight job on back navigation.
- `AiWallpaperViewModel.saveToFavorites()` stores the favorite name as `AI: ${prompt.take(60)}` and stores generated tags from the wallpaper model.
- `AiWallpaperRepository.kt` posts `prompt`, `aspect_ratio=9:16`, `output_format=png`, and optional `style_preset` to Stability's `v2beta/stable-image/generate/core` endpoint with `Authorization: Bearer <apiKey>`.
- `AiWallpaperRepository.kt` maps Stability failures into user-facing messages for invalid key, out of credits, content-policy rejection, unprocessable prompt, rate limit, and server errors.
- `AiWallpaperRepository.kt` writes generated PNGs to `filesDir/ai_wallpapers` and prunes to 50 files, but Cycle 6 already captured the raw `copyTo()` ingestion issue.
- `StabilityAiApi.kt` documents optional parts like `negative_prompt`, `cfg_scale`, and `seed`, but Aura currently exposes only prompt, style, aspect ratio, and output format.
- `ROADMAP.md` already treats per-unlock AI generation as risky because Stability calls can burn credits quickly.

External evidence reviewed:

- Stability's getting-started docs say all documented APIs use API-key authentication through the `Authorization` header and warn that API keys need to be kept secret.
- Stability's pricing page says API usage is credit-based, 1 credit equals $0.01, Stable Image Core costs credits per call, and pricing can change.
- Stability's Stable Image docs say REST v2beta is the current image-services API line and that attempts to circumvent terms or acceptable-use policies can lead to denial of service.
- Stability's Acceptable Use Policy prohibits legal-rights violations, child exploitation, sexually explicit prohibited uses, self-harm/violence/hate, safeguard circumvention, and misleading users about AI-generated outputs.
- Google Play's AI-generated content policy covers text-to-image apps and says developers are responsible for preventing offensive AI-generated content.
- Google Play's AI-generated content policy requires apps that generate content using AI to include in-app user reporting or flagging features that let users report offensive content without leaving the app.
- Android security guidance warns against putting API keys in source code and recommends Android Keystore for repeated-use secret material. Jetpack Security offers encrypted preferences/files, though the implementation choice needs a current dependency review before coding.

## Findings

### AI generation needs an explicit trust boundary

Aura currently behaves like a normal form: enter a prompt, enter a key, generate. That hides the important boundary crossing. The prompt leaves the device, the API key authenticates the user to Stability AI, and the generated image is stored locally. The app should make that visible in one compact first-use disclosure and in a persistent Settings privacy page.

Planning implication: add an AI generation disclosure gate with clear language for prompt transmission, key use, credit consumption, local generated-image storage, retention, deletion, and policy restrictions. Keep it short enough for the generation screen, but backed by `docs/privacy/ai-generation.md`.

### Google Play requires offensive-content reporting

The AI wallpaper feature is a text-to-image app feature under Google Play's AI-generated content policy. Even if Stability filters many prompts server-side, Play still requires an in-app user reporting or flagging feature for offensive generated content.

Planning implication: add a report/flag action on generated AI wallpaper results and saved AI favorites. Reports can be local-only for now if there is no backend moderation target, but the user must be able to flag content in app; release docs must say where reports go and how they inform filters/moderation.

### Bring-your-own key storage is better than bundled keys, but not finished

Aura's user-key model is the right default for OSS and third-party-cost control. However, `BuildConfig.STABILITY_AI_KEY` allows a release build to embed a Stability key if `local.properties` supplies one. DataStore backup exclusion reduces cloud-restore exposure, but DataStore preferences are not the same as encrypted secret storage.

Planning implication: add a release guard that fails if release builds bundle a nonblank Stability key unless an explicit internal-build flag is set. Document key storage and evaluate moving user-supplied Stability keys to Keystore-backed encrypted storage.

### Credit spend and retry behavior need a budget UI

Aura maps 402 out-of-credits and 429 rate-limit errors, but there is no preflight budget copy, duplicate-click guard beyond the active job, per-session/day generation count, or "same prompt again" confirmation. Cancel-on-back is useful but already notes it may not refund a credit once the request reaches billing.

Planning implication: add a small cost/rate-limit model: one generation request per tap, current provider pricing link, local generation history count, optional daily/session guardrail, and explicit copy that cancellation may not refund provider credits after the request has started.

### Prompt-derived local metadata needs a retention decision

Aura stores prompt snippets in favorite names and prompt words in tags. This is useful for search, but prompts can include sensitive context, names, places, health status, or copyrighted/brand references. Generated images are local files, but metadata still belongs in the privacy and deletion story.

Planning implication: treat prompts and prompt-derived metadata as sensitive local user content. Offer a generic favorite name by default or a prompt-retention toggle, and make deleting an AI wallpaper remove the generated file plus favorite metadata.

### On-device generation remains a decision gate

On-device generation could improve privacy and remove per-call credit spend, but it is not ready to replace Stability for Aura today. The roadmap should avoid promising local diffusion until hardware support, model licensing, storage footprint, thermal/battery behavior, moderation, and FOSS distribution implications are known.

Planning implication: keep U-2 as a research gate with concrete adoption criteria. Revisit only when a tested Android implementation fits Aura's device baseline and OSS licensing constraints.

## Roadmap Queue

- [ ] P0 - AI generation disclosure and consent gate
  - Why: Aura sends user prompts to Stability AI, uses the user's API key and credits, stores generated PNGs locally, and stores prompt-derived metadata when saved.
  - Evidence: `AiWallpaperRepository.generate()` multipart prompt/API-key call; `AiWallpaperViewModel.saveToFavorites()` prompt-derived favorite name; Stability API key and credit docs; Stability Acceptable Use Policy.
  - Touches: `AiWallpaperScreen`, Settings API-key card, Settings privacy screen, `docs/privacy/ai-generation.md`, release privacy checklist.
  - Acceptance: first AI generation shows a concise disclosure before the network call; disclosure covers prompt sharing, key/credit use, local storage, retention/deletion, and Stability policy boundaries; user can review it later in Settings.
  - Verify: first-run disclosure appears once; deny/cancel does not call Stability; accepted state persists; Settings reset/review works; privacy docs and Data safety matrix include prompt sharing and generated-image storage.

- [ ] P0 - AI-generated content report/flag path
  - Why: Google Play requires AI-generating apps to include in-app reporting or flagging for offensive generated content without requiring users to exit the app.
  - Evidence: Google Play AI-generated content policy; Aura has text-to-image generation and no report/flag action on generated results or saved AI favorites.
  - Touches: AI result screen, Favorites detail actions, report storage/diagnostics path, moderation/report docs, privacy policy.
  - Acceptance: generated AI wallpapers and saved AI favorites expose a report/flag action; report categories cover offensive/unsafe/deceptive/other; reports do not include the user's API key; release docs define retention and moderation response.
  - Verify: generate result -> report; saved favorite -> report; report survives process restart if local; report export/redaction path omits keys; Play policy checklist has an AI report row.

- [ ] P1 - BYO Stability key hardening and release guard
  - Why: User-supplied keys are appropriate, but release builds should not accidentally ship a bundled Stability key, and stored keys should have a documented security posture.
  - Evidence: `BuildConfig.STABILITY_AI_KEY` from `local.properties`; `PreferencesManager.stabilityAiKey` DataStore flow; Android security guidance on source-code API keys and Keystore.
  - Touches: release preflight, docs/privacy/API-key-storage.md, Settings key UI, diagnostics redaction test, optional encrypted-storage migration plan.
  - Acceptance: release verification fails on nonblank bundled `STABILITY_AI_KEY` unless explicitly marked internal; docs explain where keys are stored and excluded from backup; diagnostics and reports redact all provider keys; encryption migration decision is recorded.
  - Verify: static/release-preflight test with blank and nonblank keys; diagnostics export key-redaction fixture; backup/data-extraction matrix still excludes key storage.

- [ ] P1 - AI credit, rate-limit, and duplicate-generation guardrails
  - Why: Stability requests consume credits, pricing can change, and repeat taps or retries can spend user-owned credits unexpectedly.
  - Evidence: Stability pricing docs; Aura handles 402/429 after the fact; `cancelGeneration()` warns cancellation may not refund once provider billing has started.
  - Touches: `AiWallpaperViewModel`, AI screen state, Settings/provider docs, local generation history.
  - Acceptance: UI states one request may spend provider credits; active generation disables duplicate submits; retrying the same prompt/style after a recent success requires confirmation; optional local session/day count is visible; 402/429 messages link to the right provider action.
  - Verify: rapid taps create one request; same prompt retry asks confirmation; 402/429 tests still map cleanly; cancel copy does not imply refunds.

- [ ] P1 - Prompt metadata retention and deletion policy
  - Why: Aura stores prompt snippets in favorite names and prompt words in tags, which can preserve sensitive user text even after the generated image is no longer visible.
  - Evidence: `AiWallpaperRepository` mines five prompt words for tags; `AiWallpaperViewModel.saveToFavorites()` stores `AI: ${prompt.take(60)}`; Cycle 4 privacy matrix covers local user content.
  - Touches: favorite naming, tag creation, AI deletion flow, privacy/storage ledgers, Room migration if metadata fields change.
  - Acceptance: prompt-derived metadata is opt-in or easy to clear; deleting an AI wallpaper removes generated file and prompt-derived favorite/tag metadata; privacy docs classify prompts as local sensitive user content and third-party-shared request content.
  - Verify: save with sensitive prompt; clear/delete flow removes prompt text from Room and generated file; search no longer finds deleted prompt words; backup matrix matches behavior.

- [ ] P2 - On-device AI wallpaper decision gate
  - Why: Local generation could improve privacy and cost control, but it has unresolved hardware, battery, storage, licensing, and moderation constraints.
  - Evidence: U-2/U-14 roadmap notes; Qualcomm/local-dream references in Appendix D; Stability hosted generation currently shipped.
  - Touches: U-2 research, model licensing notes, performance/battery test plan, FOSS flavor strategy.
  - Acceptance: revisit criteria list required device baseline, model size, expected latency, battery/thermal budget, license compatibility, moderation/report behavior, and fallback to hosted/BYO mode.
  - Verify: no on-device generation implementation starts without meeting the criteria; any prototype includes battery/profile evidence and license review.

## Non-goals

- No implementation changes in this research pass.
- No source, tests, Gradle, workflow, resource, asset, or config edits.

## Open Questions

- Should prompt-derived favorite names default to "Generated wallpaper" with an optional "Use prompt as name" action?
- Should AI reports be stored locally/exported only, or should they feed the existing community report/moderation queue?
- Is Keystore-backed encryption worth the migration complexity for BYO provider keys, given the app already avoids automatic upload and excludes DataStore from backup?
- Should the app expose a provider-neutral AI policy screen before adding any future image/audio/video generation services?
- What local limit is reasonable: per session, per day, or only duplicate-prompt confirmation?
