# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 8
**Date:** 2026-06-04
**Repo state:** `main`, `b8b823b`, `v6.31.1-14-gb8b823b`, `versionCode 112`

## Executive Summary

Cycle 8 focused on release metadata and store-readiness. Aura now has signed GitHub release machinery, checksums, artifact attestation, an Obtainium manifest, and IzzyOnDroid prep. The remaining release risk is the user-facing and policy-facing material: Play/F-Droid-style metadata, screenshots, privacy-policy URL, content rating, target audience, user-generated-content declarations, AI-generated-content declarations, and alternate-store anti-feature explanations.

Top findings:

- P0: The committed Play/fastlane short description is 81 characters, but Google Play's short-description limit is 80 characters.
- P0: There is no tracked `docs/privacy` directory or public privacy-policy text, while Play requires all apps to provide a privacy-policy link in Play Console and a privacy-policy link or text in the app.
- P0: Aura has community uploads, AI image generation, contacts, location, microphone recording, Firebase anonymous identity, and third-party provider requests. The Play app-content pack must cover Data safety, UGC moderation, AI-generated-content reporting, content rating, target audience, and app access instructions before Play submission.
- P1: Aura has a valid 512x512 Play Store icon and one root screenshot, but no committed fastlane screenshot directories and no feature graphic. Play requires at least two screenshots and a feature graphic; Play recommends four phone screenshots at 1080px+.
- P1: Alternative-store metadata needs explicit anti-feature and sensitive-permission explanations. Aura's full build uses Firebase, Google Services, Play Services ML Kit, YouTube extraction, and third-party content APIs; this is acceptable for GitHub/Obtainium and potentially IzzyOnDroid, but must be disclosed.
- P2: Release notes, fastlane changelogs, README claims, privacy docs, and Data safety answers need one consistency gate so future implementation passes do not drift.

- `screenshot.png` is 1080x2340 and 1,489,453 bytes. It meets general screenshot dimensions, but it is only one tracked screenshot and is not placed under a fastlane screenshot folder.
- No tracked `fastlane/metadata/android/en-US/images/...` screenshots or feature graphic were found.
- No tracked `docs/privacy` directory or privacy-policy document was found.
- `.github/workflows/release.yml` builds signed release APKs, validates non-debuggable release artifacts, publishes checksums, and writes release notes with APK/signing metadata.
- `obtainium.json` points to GitHub Releases, app id `com.freevibe`, and APK filtering for release assets.
- `docs/distribution/channel-strategy.md` says Aura is full-only for GitHub/Obtainium, IzzyOnDroid is the near-term app-store candidate, and F-Droid mainline is blocked by Firebase, Google Services, and Play Services ML Kit.
- `docs/distribution/developer-verification.md` lists IzzyOnDroid submission prep but does not include screenshot/feature-graphic/privacy/content-rating details.

External evidence reviewed:

- Google Play preview-asset docs require a high-resolution app icon, short description, feature graphic, and at least two screenshots to publish a store listing.
- Google Play preview-asset docs set the app icon requirements at 512x512 32-bit PNG under 1024 KB and the short-description limit at 80 characters.
- Google Play screenshot docs allow up to eight screenshots per device type, require at least two screenshots, and recommend at least four phone screenshots at minimum 1080px resolution.
- Google Play metadata policy rejects misleading, excessive, irrelevant, improperly formatted, or inappropriate metadata, and requires clear descriptions that match app functionality.
- Google Play User Data policy requires all apps to post a privacy policy link in Play Console and a privacy-policy link or text inside the app, even if the app accesses no personal and sensitive user data.
- Google Play content rating docs require accurate questionnaire responses for new apps and for app updates when content/features change, and require target audience/content settings.
- Google Play UGC policy requires terms/user policy acceptance before upload, objectionable-content definitions, moderation, report actions, and blocking where applicable.
- Google Play AI-generated-content policy requires in-app reporting/flagging for offensive generated content, already captured in Cycle 7.
- F-Droid inclusion docs require FLOSS source-build compatibility for mainline and forbid proprietary tracking/advertising libraries, Firebase, Google Play Services, and similar proprietary dependencies.
- F-Droid metadata docs support source-repository fastlane metadata and say Latest-tab eligibility needs name, icon, summary, description, license, a What's New entry, at least one graphic, and at least one translation.
- F-Droid anti-feature docs define flags such as Non-Free Dependencies, Non-Free Network Services, Tethered Network Services, Non-Free Assets, and Tracking.
- IzzyOnDroid accepts official upstream APKs from source repositories, records signatures, scans permissions and libraries, highlights sensitive permissions, warns about cleartext traffic, and can remove apps that add too many proprietary libraries, trackers, or unresolved risky indicators.

## Findings

### Store listing metadata needs a machine-checkable gate

Aura has fastlane text metadata, but one current value is already outside Play's limit. The short description is 81 characters against Play's 80-character requirement. The title is short enough and the full description is current, but the project should not rely on manual review for these limits.

Planning implication: add a metadata preflight that checks title, short description, full description presence, changelog for the current versionCode, forbidden/stale phrases, privacy-policy URL presence, screenshot counts, and feature-graphic presence.

### Privacy policy is now a release blocker, not optional polish

Cycle 4 already found the privacy matrix need. Cycle 8 adds the distribution consequence: Play requires a privacy policy URL in Play Console and in-app privacy policy text/link for every app. Aura currently has no tracked privacy-policy document, while the app touches sensitive permissions, public community uploads, local diagnostics, AI prompts, and third-party provider requests.

Planning implication: produce `docs/privacy/privacy-policy.md` and a public non-PDF URL plan, then wire an in-app privacy screen/link. The privacy policy should draw from Cycle 4 and Cycle 7 rather than starting from generic template text.

### Play app-content declarations need one owner-ready packet

Aura is not a simple static wallpaper app. It has public user-generated uploads, AI-generated wallpapers, contact ringtone assignment, weather location, microphone recording, YouTube extraction, and anonymous Firebase community identity. These all affect Play forms and reviewer expectations.

Planning implication: create `docs/distribution/play-app-content.md` with Data safety rows, content rating questionnaire notes, target audience decision, ads declaration, UGC moderation/report/block story, AI-generated-content reporting, app access instructions, and permissions justification.

### Screenshot and graphic assets are underrepresented

The existing root screenshot is a valid portrait size, but one screenshot is not enough for Play and does not give alternate stores much confidence. There is no fastlane screenshot folder and no feature graphic. Aura's wide feature set needs a compact visual set that proves the listing claims.

Planning implication: add a reproducible screenshot plan for at least four phone screenshots: Wallpapers, Video wallpapers, Sounds/editor, and Settings/Favorites/community. Keep screenshots actual in-app UI, avoid competitor logos, avoid Play badges, and add localized alt-text notes.

### Alternative-store trust requires anti-feature disclosure

Aura's full build should be direct about its tradeoffs. It is MIT source, but not F-Droid-mainline ready because of Firebase, Google Services, and Play Services ML Kit. It also depends on non-free network services for Pexels/Pixabay/Stability and YouTube extraction behavior. IzzyOnDroid can be realistic only when those dependencies and sensitive permissions are explained up front.

Planning implication: add a channel-specific metadata matrix that maps each store/repo to required disclosures: signing/checksum, source tag, license, permissions, proprietary dependencies, network services, AI key usage, UGC moderation, cleartext status, and anti-feature candidates.

### Release copy can drift from shipped behavior

README, fastlane descriptions, changelogs, release notes, privacy docs, and Play/Data safety answers all describe overlapping behavior. Once implementation starts fixing Cycles 4, 7, and 8, the docs must stay in sync.

Planning implication: add a release metadata checklist and lightweight text checks that fail on missing current changelog, over-limit descriptions, missing privacy doc, and stale versionCode/versionName references.
