# Cycle 153 research - background work scheduling ledger

## Goal

Owner-gated live evidence is still unavailable, so this cycle advanced a local
release-hardening item: make Aura's WorkManager scheduling contract explicit
and machine-checked before implementing the full Settings diagnostics surface.

## Current app evidence

- `AutoWallpaperWorker` owns periodic unique work `auto_wallpaper` with
  `ExistingPeriodicWorkPolicy.UPDATE`, a 15-minute floor, connected or unmetered
  network, battery-not-low, optional charging, optional idle, and exponential
  15-minute backoff.
- `DailyWallpaperWorker` owns periodic unique work `daily_wallpaper` with
  `ExistingPeriodicWorkPolicy.KEEP`, 24-hour cadence, 8-hour initial delay,
  connected network, and exponential 15-minute backoff.
- `WeatherUpdateWorker` owns periodic unique work `weather_update` with
  `ExistingPeriodicWorkPolicy.KEEP`, 30-minute cadence, connected network, and
  exponential 15-minute backoff.
- `AuraOriginalsDownloader` owns one-time unique work
  `aura_originals_download` with `ExistingWorkPolicy.KEEP`, unmetered network,
  expedited execution, non-expedited fallback on quota exhaustion, and
  exponential 15-minute backoff.
- `RotationTriggerService` owns one-time unique work
  `rotation_trigger_oneshot` with `ExistingWorkPolicy.KEEP`, connected network,
  battery-not-low, expedited execution, and non-expedited fallback on quota
  exhaustion.

## Source-backed Android notes

- WorkManager `WorkRequest` objects carry constraints, scheduling information,
  retry configuration, and input data; this supports a ledger that treats
  constraints and retry/backoff as release-reviewed facts.
- WorkManager expedited work can fall back to normal non-expedited work when
  quota is exhausted via `RUN_AS_NON_EXPEDITED_WORK_REQUEST`; both Aura
  one-shot surfaces use that posture.
- WorkManager exposes distinct one-time and periodic states. Periodic work has
  only `CANCELLED` as a terminal state, so Settings diagnostics need local
  receipts for last success/failure rather than relying only on final
  WorkInfo states.
- Doze and App Standby can delay jobs, network work, and sync until maintenance
  windows; Aura diagnostics should label those as possible deferral reasons
  rather than provider failures.

## Implementation decision

Added a checked scheduling ledger first instead of changing runtime behavior.
The ledger closes the P1 unique-work policy matrix and partially advances the
P0 background-work status item. The remaining P0 work is the app-facing
diagnostics surface and support-bundle section that read WorkInfo plus local
worker receipts.

## Verification plan

- `tools/background_work_scheduling_check.py` validates the ledger schema,
  required work rows, unique work names, source terms, docs, source URLs, and
  workflow/runbook wiring.
- Focused tests cover the live ledger plus missing row, source-policy drift,
  weak deferral list, missing source URL, and missing workflow command cases.
- Release metadata and workflow security policy include the new preflight so
  the command cannot silently disappear from verify/release.
