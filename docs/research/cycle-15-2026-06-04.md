# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 15
**Date:** 2026-06-04
**Repo state:** `main`, `89c65a2`, `versionCode 112`

## Executive Summary

Cycle 15 focused on network security, cleartext exceptions, and provider credential handling. Aura has an app-level `android:usesCleartextTraffic="false"` posture, but `network_security_config.xml` still permits cleartext for all `ccmixter.org` subdomains and `CcMixterRepository` falls back from TLS failure to an HTTP API call. That exception now needs to be treated as a release-blocking security posture item, not only a provider-specific compatibility workaround.

Credential handling is the second half of the risk. `app/build.gradle.kts` can bake Pexels, Pixabay, Freesound, SoundCloud, and Stability AI values from `local.properties` into `BuildConfig`. Some are optional provider keys, some are user-entered DataStore values, and some are sent as query parameters that can easily leak through URL logging, diagnostics, media URLs, or bug reports. Aura already has useful backup exclusions and crash-diagnostics redaction, but there is no release guard proving distributed APKs contain no bundled third-party keys, and no provider credential matrix tying storage, transmission, logging, backup, and diagnostics behavior together.

Top findings:

- P0: A release build should not allow the ccMixter HTTP fallback by default. The current network-security config permits cleartext for `ccmixter.org`, and the repository intentionally retries over HTTP on `SSLException`.
- P0: Release builds can silently embed provider credentials from a developer's `local.properties` into `BuildConfig`. This is especially risky for paid or quota-bearing providers such as Stability AI, and it is inconsistent with the documented user-supplied-key model.
- P1: User/API keys are stored in DataStore and excluded from cloud/device backup, but they are not protected by Android Keystore-backed encryption. That may be acceptable for optional low-value public API keys, but the decision needs to be explicit per key type.
- P1: Wallhaven, Pixabay, Freesound, and SoundCloud place credentials or client IDs in query strings, while Pexels and Stability use headers. Query credentials must be treated as sensitive in logs, diagnostics, source metrics, stream URLs, and support bundles.
- P1: Crash diagnostics redaction covers Bearer tokens, authorization headers, assignment-style secrets, query parameters named `key`/`token`/`client_id`, and app-private paths. The gap is test coverage with provider-specific fixtures and media URL examples.
- P2: Debug-only OkHttp `BASIC` logging avoids headers/bodies, but a central "no raw URL with credentials" logging rule would keep future diagnostics and source-health screens from regressing.

## Current State

Local evidence reviewed:

- `AndroidManifest.xml` sets `android:usesCleartextTraffic="false"` and references `@xml/network_security_config`.
- `network_security_config.xml` permits `cleartextTrafficPermitted="true"` for `ccmixter.org` with `includeSubdomains="true"`.
- `CcMixterRepository.fetchUploads()` catches `SSLException` and calls `fetchUploadsOverHttp()`. `buildCcMixterFallbackUrl()` constructs `http://ccmixter.org/api/query?...`.
- `app/build.gradle.kts` reads `local.properties`, then writes `PEXELS_API_KEY`, `PIXABAY_API_KEY`, `FREESOUND_API_KEY`, `SOUNDCLOUD_CLIENT_ID`, and `STABILITY_AI_KEY` into `BuildConfig`.
- `docs/distribution/release-signing.md` says the GitHub release workflow writes blank optional provider keys and warns not to commit `local.properties`, but there is no local release guard preventing a developer-built release APK from embedding keys.
- `PreferencesManager` reads optional user/provider values from DataStore. Pexels, Pixabay, Freesound, and Stability fall back to `BuildConfig` values; Wallhaven is user-only; SoundCloud reads only `BuildConfig.SOUNDCLOUD_CLIENT_ID`.
- `backup_rules.xml` and `data_extraction_rules.xml` exclude `datastore/freevibe_prefs.preferences_pb` and `crash.log` from cloud backup and device transfer, reducing backup exposure for DataStore API keys and diagnostics.
- `CrashDiagnosticsCollector` sanitizes Bearer tokens, authorization headers, assignment-style secrets, query-string secrets (`api_key`, `apikey`, `key`, `access_token`, `token`, `client_id`, `password`, `secret`), `file://` paths, and app-private paths.
- Provider credential transport varies:
  - Wallhaven: `apikey` query parameter.
  - Pixabay: `key` query parameter.
  - Freesound: `token` query parameter.
  - SoundCloud: `client_id` query parameter and embedded stream URLs.
  - Pexels: `Authorization` header.
  - Stability AI: `Authorization: Bearer <key>` header.
- `AppModule` adds OkHttp `HttpLoggingInterceptor.Level.BASIC` only for debug builds, then adds a common User-Agent and Freesound rate-limit interceptor.

External evidence reviewed:

- Android's cleartext-communications risk page says cleartext traffic can be observed and modified by anyone monitoring the network, and recommends setting cleartext traffic disabled in network security config.
- Android Network Security Configuration docs support per-domain cleartext configuration and debug-only overrides, but the intended safety posture is explicit, narrow configuration rather than broad app-wide cleartext.
- Android's security checklist says API-key storage is a critical part of data protection and recommends defense in depth with Android Keystore and encryption for stored keys.
- Android Keystore docs describe using system-backed key material and authorizations so key use can be constrained outside the app process.
- Pexels uses an `Authorization` header for API keys.
- Pixabay requires a `key` parameter for API calls.
- Freesound API v2 token authentication uses a `token` request parameter.
- Stability's developer docs use API-key authorization for image generation, and prior Cycle 7 research recorded the need to keep those keys secret and user-supplied.

## Findings

### The ccMixter HTTP fallback is now a release posture issue

The app's manifest says cleartext is disabled, but the network security config makes a domain exception, and `CcMixterRepository` intentionally uses it. A TLS failure should not automatically downgrade a release user to HTTP content-provider metadata or media discovery. Even if ccMixter's API availability motivated the fallback, this is now a distribution trust issue: release reviewers, Izzy-style scanners, and security-conscious users will see cleartext as an anti-feature or risk indicator.

Planning implication: remove the fallback for release builds, move it behind a debug/internal provider-policy flag, or disable ccMixter when HTTPS fails. If a temporary exception remains, it needs a documented owner, expiration, user-visible degraded-source state, and a static check that no other cleartext domains or `http://` API URLs appear.

### BuildConfig provider keys need a release guard

The release workflow writes blank optional provider keys, but local release builds can still bake a developer's `local.properties` values into the APK. This is not only a source-control concern. APKs are distributed to untrusted devices and can be inspected, so bundled keys should be treated as published credentials. The user-entered-key model is compatible with OSS distribution; a hidden bundled-key model is not.

Planning implication: add a release preflight that fails when any provider key or client ID is nonblank unless an explicit internal distribution flag is set. Then scan the built APK for sentinel/fake keys to prove the guard works. Stability AI should be the strictest because it is credit-bearing and user-prompt-driven.

### DataStore exclusion is not the same as encrypted local secret storage

Aura excludes DataStore from cloud backup and device transfer, which is a good privacy baseline. However, user-entered provider keys still live in ordinary app-private storage. App-private storage protects against normal cross-app access, but it does not provide Keystore-backed encryption or hardware-backed key-use restrictions.

Planning implication: define a per-provider key class. Low-value public/client IDs may remain DataStore-only with clear disclosure; paid or quota-bearing API keys should either use Keystore-backed encrypted storage or explicitly document why Aura does not promise stronger at-rest protection.

### Query-string credentials need a no-raw-URL rule

Several providers require query parameters for authentication, and SoundCloud stream URLs embed `client_id`. Query strings are more likely than headers to show up in logs, exception messages, URL cache keys, source health views, media URLs, screenshots, and support bundles. Current crash redaction is a strong start, but future logging paths can bypass it.

Planning implication: centralize redacted URL formatting and require it for diagnostics, metrics, exceptions, source-health cards, and tests. Prefer header authentication when a provider supports it, but where providers require query parameters, never persist or display full authenticated URLs.

### Diagnostics need provider-specific redaction fixtures

`CrashDiagnosticsText.sanitize()` covers the right classes of tokens in broad regexes. The missing evidence is fixtures for real provider shapes: `?apikey=...`, `?key=...`, `?token=...`, `?client_id=...`, `Authorization: Bearer ...`, `apiKey=...`, `stability.ai.key=...`, `local.properties`, and SoundCloud/Freesound stream URLs. This matters because diagnostics are explicitly user-copyable and are likely to appear in GitHub issues.

Planning implication: add regression tests that build a synthetic crash log from every provider credential format and assert the exported bundle contains only redacted values.

## Verification Targets

- Release build fails when `local.properties` contains nonblank provider keys unless an explicit internal-only override is supplied.
- A generated release APK is scanned for sentinel provider key strings and the scan proves they are absent.
- Static scan fails on `cleartextTrafficPermitted="true"` and `http://` provider URLs unless the provider-policy allowlist explicitly permits them.
- ccMixter search either succeeds over HTTPS or reports a disabled/degraded source state without falling back to HTTP in release.
- Diagnostics fixtures prove all provider-specific token/header/query/client-ID forms are redacted.
- Backup/data-transfer rules are compared to the credential-storage matrix after a smoke run with every key set.
