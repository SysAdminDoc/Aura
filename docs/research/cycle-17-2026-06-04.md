# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 17
**Date:** 2026-06-04
**Repo state:** `main`, `050c847`, `versionCode 112`

## Executive Summary

Cycle 17 focused on third-party license notices, native/bundled dependency attribution, provider/content-source disclosure, and distribution-ready compliance evidence. Aura already has a Licenses screen and a high-level README note, but the current surface is hand-maintained and covers only a subset of the runtime dependency graph and content-source matrix.

Top findings:

- P0: The Licenses screen is static and incomplete. It lists core AndroidX/Square libraries and NewPipe Extractor, but the release dependency graph also includes Firebase, Google Play services ML Kit/base, ZXing, Kotlin coroutines/serialization, AndroidX ProfileInstaller, Palette, desugaring, youtubedl-android, and its FFmpeg artifact. There is no generated notices workflow or release gate.
- P0: Copyleft/native distribution needs a dedicated compliance packet. NewPipe Extractor is GPL-3.0, youtubedl-android is GPL-3.0 and bundles yt-dlp/Python payloads, and the FFmpeg artifact can carry LGPL/GPL obligations depending on the binary configuration. The current docs acknowledge native/FFmpeg/youtubedl SBOM scope but defer generation.
- P1: `ContentSource` has more sources than the Licenses screen discloses. Audius, ccMixter, SoundCloud, Wikimedia, Internet Archive, NASA, Picsum, Klipy, Community, Bundled, AI-generated, and Local are absent from the content-source list even though they are source enum values or runtime surfaces.
- P1: Item-level license/provenance is not preserved uniformly. Sounds can display license/uploader/source links, but favorites do not persist sound license, wallpapers have no license field, and bundled "Aura Picks" hides the upstream Freesound creator behind a generic uploader label.
- P1: Alternate-store and user-trust disclosures should be generated from the same source as the in-app notices. F-Droid anti-feature labels and Google Play IP policy both make hidden or drifting provider/content disclosures risky for a mixed-source personalization app.

External evidence reviewed:

- Google Play services open-source notice docs say developers are responsible for displaying notices for open-source libraries used in an app, and Google provides `oss-licenses-plugin` plus `play-services-oss-licenses` to collect and display notices from app dependencies.
- The same Google docs say the plugin scans Maven POM license metadata at compile time and packages license data into the app.
- FFmpeg's official legal page says FFmpeg is LGPL 2.1-or-later by default, but GPL-covered optional parts can make the whole FFmpeg binary GPL; its compliance checklist includes exact-source distribution for the binaries shipped.
- youtubedl-android's GitHub repository identifies it as an Android wrapper for yt-dlp, publishes the `library` and `ffmpeg` artifacts used by Aura, notes bundled yt-dlp/Python payloads, and is GPL-3.0 licensed.
- NewPipeExtractor's GitHub repository identifies it as a library for extracting data from streaming sites, supports YouTube and SoundCloud among others, and is GPL-3.0 licensed.
- F-Droid anti-feature docs describe user-visible labels for non-free assets, non-free dependencies, non-free network services, tethered network services, and tracking.
- Google Play's intellectual-property policy disallows apps that infringe copyright or encourage copyright infringement, including apps that encourage unauthorized downloading of copyrighted music or video.
- SPDX describes SBOMs as a standard way to communicate component, provenance, license, security, and related supply-chain metadata.

## Findings

### Generated notices are now a release-readiness gap

Aura's static Licenses screen is useful as a first pass, but it is already behind the dependency graph. The gap is not just a missing row problem. A hand-maintained list cannot reliably reflect transitive dependencies, Google Play services dependencies, native packages, or future version bumps. Because the release workflow already publishes side-loadable APKs, the license surface should become part of release verification.

Planning implication: add a generated notice lane that inventories release runtime dependencies, packages an in-app notice surface or notice file, and fails release preflight when a dependency lacks notice metadata or when static rows drift from the dependency graph.

### Copyleft and native artifacts need a separate packet

NewPipe Extractor, youtubedl-android, yt-dlp payloads, Python payloads, and FFmpeg are not ordinary permissive Android dependencies. They create distribution questions around exact source, license text, binary provenance, FFmpeg configuration, update behavior, and channel-specific disclosures. `docs/distribution/supply-chain.md` already names native/FFmpeg/youtubedl-android SBOM scope, but the current release path has no packet tying artifacts to licenses, source URLs, versions, and source-offer requirements.

Planning implication: treat this as P0 before the next public release expansion. The implementation can still avoid legal interpretation, but it should produce factual release evidence: artifact coordinates, upstream URLs, license IDs, binary/source correspondence, FFmpeg build mode, and where users can find the required notices/source.

### Content-source disclosure should be generated from `ContentSource`

The code's source enum is wider than the UI disclosure. Some missing sources may be dormant, legacy, or local-only, but users and distributors should not need to infer that from code. A matrix that maps each source to license/terms, attribution fields, allowed actions, cache policy, provider toggle, and anti-feature implications would also close gaps from Cycles 3, 8, 13, and 15.

Planning implication: generate or test the Licenses/Provider Policy source list against `ContentSource`. If a source is dormant, label it disabled/legacy in the matrix rather than omitting it.

### Item-level license metadata can be lost after save/export flows

Sound detail can show license data when the active `Sound` carries it, but favorites lose that field. Wallpaper detail has source/uploader affordances but no license field. Export schemas do not yet define license/provenance compatibility. That means a user can save, export, restore, or import content and lose the information needed to decide whether an action is permitted.

Planning implication: extend the provenance model and export schemas so normalized license and source-page metadata survive favorites, collections, downloads, imports, exports, and local restoration.

### Bundled content needs upstream attribution, not only an Aura label

The bundled Aura Picks currently use Freesound CC0 source URLs, but the visible uploader is "Aura Picks" and the Sound detail screen suppresses the uploader for that bundled label. For a curated built-in pack, the UI can still brand it as Aura Picks, but the legal/provenance layer should retain the original creator/source ID/license so the app and release notices are accurate.

Planning implication: add curation metadata with upstream creator, source asset URL, source license, review date, and bundling rationale. The UI can show concise "Aura Picks, sourced from Freesound" copy without hiding provenance.

### Store and repository metadata need the same source of truth

Google Play IP policy, IzzyOnDroid review, F-Droid anti-feature labeling, GitHub release notes, and in-app notices all ask related questions in different forms. Maintaining those answers separately creates drift. The same matrix used for generated notices should drive release metadata, README/legal docs, and alternate-store disclosures.

Planning implication: add a single third-party notice/provider disclosure source of truth and release checklist step. It should feed the in-app Licenses screen, `docs/legal/third-party-notices.md`, release notes, and any F-Droid/Izzy anti-feature declarations.

## Recommended Roadmap Insertions

1. P0 - Generated OSS notices and license drift gate.
2. P0 - Copyleft/native extractor compliance packet for NewPipe, youtubedl-android, yt-dlp/Python payloads, and FFmpeg.
3. P1 - Runtime dependency and content-source coverage matrix generated from Gradle and `ContentSource`.
4. P1 - Preserve item-level license/provenance through favorites, collections, downloads, imports, and exports.
5. P1 - Provider/store anti-feature disclosure source of truth.
6. P2 - Bundled/Aura Picks curation metadata and upstream attribution policy.

## Verification Targets

- A release preflight task generates third-party notices from release runtime dependencies and fails on missing or changed license metadata.
- The APK contains or links to a generated notice artifact, and Settings can display it without relying solely on hard-coded rows.
- Changing a runtime dependency version or adding a new dependency creates a notice diff that must be reviewed.
- A native/copyleft packet lists NewPipe Extractor, youtubedl-android, bundled yt-dlp/Python payloads, FFmpeg, versions, source URLs, license IDs, and source-offer locations.
- A test compares `ContentSource.entries` to the provider/license matrix and fails when a source is missing.
- Favorites, downloads, collections, and export/import fixtures preserve normalized source license and original source page metadata.
- Bundled content manifests include upstream creator/source/license fields and the UI exposes a concise source/provenance affordance.
