# Cycle 65 - Storage Lifecycle and Orphan Cleanup Policy

## Scope

Cycle 65 defines the first Cloud Storage lifecycle/orphan cleanup policy for
Aura community uploads. It deliberately avoids automatic delete rules on
committed public upload prefixes and adds an offline orphan-report tool for
operator-reviewed cleanup.

## Primary Sources

- Cloud Storage lifecycle management:
  https://docs.cloud.google.com/storage/docs/lifecycle
- Cloud Storage deleting objects:
  https://docs.cloud.google.com/storage/docs/deleting-objects
- Firebase Storage Android delete files:
  https://firebase.google.com/docs/storage/android/delete-files

## Local Evidence

- Committed community upload blobs currently live under `sounds/{uid}/...` and
  `wallpapers/{uid}/...`.
- Public RTDB metadata now stores `storagePath` for new community sound and
  wallpaper uploads.
- Upload repositories already try immediate best-effort Storage deletion when
  metadata save fails after a blob upload.
- Owner/admin delete flows now delete Storage objects directly and treat
  already-missing objects as removable.
- Cloud Storage lifecycle rules can match prefixes and age, but they cannot
  prove that a committed object is unreferenced by RTDB metadata.

## Implementation

- Added `tools/community_storage_orphan_report.py` to compare exported Storage
  object names with exported RTDB community metadata.
- Added `test/tools/community_storage_orphan_report_test.py` covering orphan
  candidates, metadata rows that reference missing objects, legacy rows missing
  `storagePath`, wrong-prefix metadata rows, unmanaged objects, and plain string
  Storage exports.
- Wired `.github/workflows/verify.yml` so backend lifecycle/tool changes run the
  orphan-report unittest in the Firebase backend CI path.
- Added `docs/community-storage-lifecycle-policy.md` defining the no-automatic-
  delete policy for committed prefixes, the two-report manual deletion gate, and
  the future temporary-prefix lifecycle rule.
- Linked the lifecycle policy from community upload deletion, Firebase rules
  harness, and backend deploy/rollback runbooks.
