# Cycle 110 Research - Android Follow Callable Migration

## Goal

Move Android creator follow and unfollow writes from direct Realtime Database
first-write behavior to the existing `setCreatorFollow` callable when Firebase
Auth is available, while keeping compatibility fallback until deploy evidence
and direct-rule tightening are complete.

## Local Evidence

- `functions/src/followHandler.ts` accepts an envelope with `operationId`,
  `clientSentAt`, and a payload containing `creatorId`, `label`, and
  `following`.
- The backend derives follower UID from Firebase Auth, requires App Check,
  normalizes creator text, derives the sanitized `creatorKey`, treats already
  matching follow state as a duplicate success, reserves quota, writes or
  removes `/creator_follows/{uid}/{creatorKey}`, and records a dedupe marker.
- `CommunityQuotaPolicies.follows` maps follows to `setCreatorFollow`, final
  writes `/creator_follows/{uid}/{creatorId}`, and standard App Check token
  use.
- `CreatorProfileRepository.followCreator()` and `unfollowCreator()` still
  wrote directly to `/creator_follows` before Cycle 110.

## Implementation

- Added `CommunityFollowInput` and `buildCommunityFollowCallablePayload()` so
  Android sends only normalized public creator fields plus desired state.
- Added `CommunityCallableClient.setCreatorFollow()` with `follow_` and
  `unfollow_` operation IDs.
- Updated `CreatorProfileRepository` so follow and unfollow:
  - Ensure community source state and identity before selecting a write path.
  - Call `setCreatorFollow` first when Firebase Auth has a current UID.
  - Treat `accepted` and `duplicate` callable responses as successful desired
    state.
  - Do not fall back to direct RTDB for quota, Auth, App Check, validation, or
    unexpected callable status failures.
  - Preserve the existing direct RTDB set/remove path only when the callable
    endpoint is missing or Firebase Auth is unavailable.
- Extended `CommunityCallableClientTest` for follow and unfollow envelopes,
  desired-state payloads, label normalization, and non-limited-use token
  selection.

  evidence, full callable wire-protocol coverage, and direct RTDB rule
  tightening.
