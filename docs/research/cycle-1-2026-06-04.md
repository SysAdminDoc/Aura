# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 1
**Date:** 2026-06-04
**Repo state:** `main`, `v6.31.1`, `versionCode 112`

## Executive Summary

Aura is a Kotlin/Jetpack Compose Android personalization app covering wallpapers, video wallpapers, live wallpapers, ringtones, notifications, alarms, community uploads, creator profiles, and source aggregation. The strongest current shape is breadth: it already has five product tabs, Firebase-backed community data, Photo Picker migration, Smart Crop, Tasker hooks, lockscreen widget surface, and CI verification. The highest-value direction for this cycle is trust and release quality: harden anonymous Firebase upload/write surfaces with App Check, make the "instant startup" claim measurable with Baseline Profile/Macrobenchmark/JankStats, and prepare the GitHub/Obtainium/F-Droid distribution path for Android developer verification and Play foreground-service review.

Top opportunities:

- P0: Firebase App Check with Play Integrity for Realtime Database and Cloud Storage writes.
- P1: Baseline Profile + Macrobenchmark + optional JankStats gate for startup and grid jank.
- P1: Android developer verification and signed artifact provenance for non-Play distribution.
- P1: Foreground-service `specialUse` policy review for rotation triggers, with exact-alarm/WorkManager fallback planning.
- P1: Content-source attribution, provenance, and takedown/report queue for community and third-party catalog entries.
- P2: Video wallpaper playlists and per-video behavior profiles, folded behind the existing GL/AGSL engine work.

## Competitive and Ecosystem Research

- Muzei: mature open-source live wallpaper with a provider API. Learning: Aura should continue NX-5 around a versioned provider contract and guard providers with explicit permissions.
- Doodle: FOSS live wallpaper emphasizes power-efficient animations, direct boot, no ads, and no analytics. Learning: Aura's "polite live wallpapers" charter is aligned; keep battery dashboard and no-tracking stance visible.
- UndeadWallpaper: focused FOSS video wallpaper app with playlists, loop/shuffle, one-shot, and start-time behavior. Learning: Aura's video surface can leapfrog by adding playlists only after the GL/AGSL/ExoPlayer engine reduces service complexity.
- Zedge: commercial/community competitor with wallpapers, ringtones, parallax, rotation, community uploads, and large scale; upload docs require an account and metadata. Learning: Aura should not copy monetization, but should copy stronger contributor provenance and moderation controls.
- Backdrops: commercial wallpaper app paywalls ad-free and Explore save/pro packs. Learning: Aura can differentiate by preserving no-ads/no-subscriptions while offering curated "Aura Originals" content and transparent provenance.
- Pexels/Pixabay: official API docs expose creator/source metadata and require or encourage attribution/linkbacks; Pexels explicitly warns against replicating a wallpaper app from Pexels content. Learning: Aura should surface source-page links and source-specific compliance text consistently.

## Highest-Value New Features

### Firebase App Check for community writes

- User problem solved: anonymous uploads/votes are cheap to automate, and Custom Claims only protect admin moderation, not backend resource abuse.
- Evidence: `database.rules.json` allows authenticated writes to community data; `app/build.gradle.kts` includes Firebase Auth/Database/Storage but no App Check Play Integrity dependency. Firebase App Check supports Realtime Database and Cloud Storage and recommends monitoring metrics before enforcement.
- Proposed behavior: add App Check Play Integrity in release builds and debug provider support in debug/CI; monitor App Check request metrics; enable enforcement for RTDB and Storage after a measured burn-in.
- Implementation areas: `gradle/libs.versions.toml`, `app/build.gradle.kts`, `FreeVibeApp.kt`, Firebase console setup, `docs/firebase-admin-claims.md`, new `docs/firebase-app-check.md`.
- Risks and edge cases: Play Integrity quota/false negatives, emulator/dev builds, F-Droid/side-loaded distribution, older devices without Play services.
- Verification plan: emulator/debug provider write tests; manual upload/vote from debug and release builds; Firebase metrics checked before enforcement; RTDB/Storage enforcement toggled gradually.
- Complexity: M.
- Priority: P0.

### Baseline Profile, Macrobenchmark, and JankStats gate

- User problem solved: Aura claims instant startup and smooth grids, but there is no benchmark module or release profile to make that measurable.
- Evidence: no `androidx.benchmark`, `BaselineProfile`, or `JankStats` dependencies were found in tracked source/manifests; Android docs report Baseline Profiles optimize startup and runtime critical paths and recommend Macrobenchmark for critical user journeys.
- Proposed behavior: add a `benchmark`/`baselineprofile` module, generate startup and journey profiles for Wallpapers, Videos, Sounds, Favorites, and Wallpaper Detail, and add optional debug-only JankStats diagnostics.
- Implementation areas: settings.gradle, app/build.gradle.kts, gradle version catalog, new benchmark module, CI workflow, Settings diagnostics.
- Risks and edge cases: needs physical device for reliable performance measurements; benchmark CI can be flaky; profiles should stay below size limits and not overfit transient UI.
- Verification plan: `generateBaselineProfile`, Macrobenchmark startup/scroll runs on a physical device, compare profile/no-profile startup and frame metrics, upload reports as CI artifacts.
- Complexity: M.
- Priority: P1.

### Android developer verification and signed artifact provenance

- User problem solved: Aura distributes outside Play, and Android's developer verification rollout begins in September 2026 in select regions before expanding globally.
- Evidence: Aura currently uses GitHub Releases/Obtainium and plans F-Droid/Izzy; Android developer verification docs say apps on certified devices in initial regions must be registered by a verified developer starting September 2026.
- Proposed behavior: fold verification into NX-8 distribution work: register `com.freevibe`, document signing-key continuity, publish checksums/SBOM/provenance, attach all split APKs and universal APKs, and explain install paths for Play, GitHub, Obtainium, Izzy, and F-Droid.
- Implementation areas: `obtainium.json`, `fastlane/metadata`, release workflow, docs/distribution, GitHub release templates, signing docs.
- Risks and edge cases: owner identity steps cannot be completed by code; F-Droid constraints may conflict with Firebase/yt-dlp; limited distribution accounts cap installs.
- Verification plan: registered package visible in Android Developer Console/Play Console; release artifacts have SHA-256 checksums; Obtainium update test succeeds; Izzy/F-Droid submission status documented.
- Complexity: M.
- Priority: P1.

### Foreground-service policy review for rotation triggers

- User problem solved: per-unlock/screen-off rotation uses a long-lived `specialUse` foreground service; Play review can reject insufficiently justified special-use declarations.
- Evidence: `AndroidManifest.xml` declares `FOREGROUND_SERVICE_SPECIAL_USE`, `RotationTriggerService`, and `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`; Android docs require a manifest property and state that special-use cases are reviewed in Play Console.
- Proposed behavior: create a policy-ready runbook and tighten implementation acceptance around only running foreground service while user-enabled triggers are active, clear notification text, branch to exact alarm/WorkManager where possible, and document Play declaration text.
- Implementation areas: `RotationTriggerService.kt`, Settings rotation copy, `app/src/main/AndroidManifest.xml`, `fastlane/metadata`, `docs/distribution`.
- Risks and edge cases: exact-alarm permissions also have policy constraints; background limits vary by OEM; user confusion if notification permission is denied.
- Verification plan: opt-in/off transitions start/stop service; Play Console declaration text reviewed; manual background behavior tested on Android 14+ and low-battery/doze scenarios.
- Complexity: S/M.
- Priority: P1.

### Content provenance, attribution, and report queue

- User problem solved: users and moderators need to understand source/license/creator provenance and report problematic community content without turning Aura into a marketplace.
- Evidence: existing models map `sourcePageUrl`, `uploaderName`, and sound `license`; Pexels and Pixabay expose source and contributor metadata; YouTube branding rules require source attribution in mixed-source apps; Zedge requires community upload accounts and metadata.
- Proposed behavior: add a provenance panel on wallpaper/sound details, normalize source-specific attribution text, add "Report content" for community entries, and persist moderator queue records in Firebase with Custom Claim admin resolution.
- Implementation areas: models/entities, `WallpaperDetailScreen.kt`, `SoundDetailScreen.kt`, `VoteRepository`/new moderation repository, RTDB rules, licenses screen.
- Risks and edge cases: avoid legal conclusions in UI; protect reporters' privacy; prevent report spam via App Check and rate limiting.
- Verification plan: source panels render for Pexels/Pixabay/Reddit/YouTube/community/bundled items; report queue accepts only authenticated/App-Checked users; admin can hide/unhide with rules tests.
- Complexity: M.
- Priority: P1.

### Video wallpaper playlists and behavior profiles

- User problem solved: users with multiple local clips need shuffle/loop-all/one-shot modes without repeatedly reapplying a single video.
- Evidence: UndeadWallpaper's focused video app exposes drag/drop playlists, loop/shuffle, smart start times, and one-shot mode; Aura currently has local import, crop, Fit/Fill, and battery dashboard but no persistent video playlist profile.
- Proposed behavior: after NX-1 engine migration, add a video-wallpaper profile containing ordered clips, per-clip crop/fit/FPS, shuffle/loop/all/one-shot mode, and start-time behavior.
- Implementation areas: Room entity/migration, VideoWallpapersViewModel, VideoWallpaperService/GL engine, settings/apply sheet.
- Risks and edge cases: storage growth, battery drain, media permission persistence, migration from single-video prefs.
- Verification plan: create/edit/reorder playlist, apply, reboot, unlock behavior, low-battery FPS cap, delete missing media gracefully.
- Complexity: L.
- Priority: P2.

## Existing Feature Improvements

- NX-8 distribution should be expanded with Android developer verification, artifact checksums, and branch protection.
- NX-6 rotation triggers should be expanded with a foreground-service policy runbook and exact-alarm fallback decision.
- L-8 true offline/cold-start work should be promoted or split so Baseline Profiles and Macrobenchmark land before further UX claims.
- N-2 Custom Claims should be followed by App Check; claims authorize admins, App Check protects backend resources from non-Aura clients.
- T-E content authenticity should become an implementable provenance/report queue item, not only a theme.

## Reliability, Security, Privacy, and Data Safety

- App Check is the highest-value new backend hardening item because anonymous Firebase Auth is not proof that writes come from Aura.
- yt-dlp CVE-2026-26331 remains a risk-register item even if Aura does not use `--netrc-cmd`; keep a guard test around options passed to yt-dlp.
- NewPipeExtractor latest viewed release is v0.26.2 while Aura pins v0.24.8; dependency refresh should stay tied to N-1 build verification.
- `RotationTriggerService` special-use foreground service needs review evidence and an owner-visible Play Console declaration.
- Local Gradle verification is blocked by missing Android SDK; CI exists but branch protection is not confirmed.

## UX, Accessibility, and Trust

- Trust should be visible: source panels, contributor/source links, report action, and "why this permission is needed" copy for notifications/location/contacts/write settings.
- Baseline Profile/Macrobenchmark work should include scroll flows for dense grids because Aura's primary user action is scanning and comparing content cards.
- Provenance UI should use compact badges and "View source" links without cluttering the primary apply/share flow.
- Video playlist work should not ship until there is clear missing-media, battery, and low-storage recovery UX.

## Architecture and Maintainability

- App Check should be isolated behind initialization helpers and docs so debug provider and Play Integrity provider do not leak into each other.
- Benchmark/Profile work should be a separate module, not app production code.
- Distribution verification should live in docs/release/distribution guidance and release workflow metadata, not scattered comments.
- Provenance/report queue should use typed models and Firebase rules tests rather than ad hoc string flags.
- Video playlists should wait for engine consolidation to avoid deepening single-video `SharedPreferences` debt.
