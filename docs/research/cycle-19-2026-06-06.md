# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 19
**Date:** 2026-06-06
**Repo state:** `main`, uncommitted Cycle 18 roadmap updates present, `versionCode 112`

## Executive Summary

Cycle 19 refined Cycle 18's generated-notices plan into a safer implementation sequence for Aura's current toolchain. The key discovery is that the newest AboutLibraries 15.x line is not a current-toolchain fit: its release notes make AGP 8.13 the minimum, while Aura is on AGP 8.7.3 and Gradle 8.12. That does not block the notice gate, but it changes the recommended first slice.

Recommended sequence:

1. Current toolchain: prototype Google Play services OSS notices and/or AboutLibraries 14.2.1 in a local branch/mirror.
2. Current toolchain: add a custom release-runtime dependency inventory task or script that compares generated notice output to a curated overlay.
3. Current toolchain: add native/copyleft AAR/APK inspection as a custom script, independent of notice plugins.
4. Post N-1: revisit AboutLibraries 15.x and a full CycloneDX/SPDX lane after AGP/Gradle/Kotlin upgrades.

## Findings

### AboutLibraries 15 belongs after N-1

Aura's current AGP pin is 8.7.3. AboutLibraries 15.x currently requires AGP 8.13, so adopting the newest Android plugin before N-1 would turn the notice pass into a toolchain upgrade. That is exactly what Cycle 18 tried to avoid. AboutLibraries 14.2.1 is the better candidate for a current-toolchain test if Aura wants generated resources for its custom Compose Licenses screen.

Planning implication: change Cycle 18 acceptance language from "use AboutLibraries latest" to "test AboutLibraries 14.2.1 on current AGP; move to 15.x only after N-1".

### Google OSS notices are the lowest-risk first experiment

Google's plugin is specifically documented for Android apps, Google Maven, Kotlin DSL, and the current runtime library. Aura already depends on Firebase/Play-services artifacts, so it should be tested as a quick proof of POM-derived notices. It may not produce the Compose-native UI Aura wants, but it can prove notice extraction and packaged assets with less ecosystem uncertainty.

Planning implication: first prototype should add the settings `resolutionStrategy`, plugin application, `play-services-oss-licenses`, and a Settings row that opens `OssLicensesMenuActivity` or compares the generated asset. If the stock activity is visually unacceptable, keep the generated asset and move rendering to a later custom UI step.

### License gate can start as a custom diff before adopting a policy plugin

Aura's most important enforcement need is simple: direct release-runtime dependency changes should produce a reviewed notice/inventory diff. A custom script that runs Gradle dependency reporting or parses generated notice JSON/assets may be enough for the first gate. That avoids introducing a policy plugin before compatibility is verified.

Planning implication: add `tools/license_notice_check.py` or a Gradle task that writes a stable JSON snapshot with group, name, version, license title/URL, source URL where known, and overlay status. The release/CI gate can compare it to `docs/legal/dependency-notices.lock.json`.

### Native payload inspection should stay tool-independent

No Maven notice plugin will answer which binaries/assets youtubedl-android and FFmpeg actually ship into the APK. This should be implemented as a script that inspects resolved AARs and release APKs, independent of Google OSS notices, AboutLibraries, Licensee, CycloneDX, or SPDX.

Planning implication: create a script that can run after `assembleRelease` in CI and in a lighter AAR-only mode locally. The local mode can inspect Gradle cache artifacts if resolved; the CI mode can additionally inspect the packaged APK.

### The release workflow has a clean insertion point

The release workflow currently builds, packages, verifies, checksums, attests, writes release notes, uploads artifacts, and attaches APK/checksums on tags. Notice/SBOM/native-packet generation should happen after the signed APK exists and before release notes/upload, because the generated release notes can then include the artifact names and links.

Planning implication: future implementation should add steps between "Verify release APK" and "Generate checksums" or between "Generate checksums" and "Generate release notes", depending on whether notice artifacts should be included in checksums.

## Verification Targets

- `./gradlew --no-daemon --max-workers=2 :app:tasks` or an equivalent lightweight command can load the build after each plugin experiment.
- Google OSS notices spike proves whether `oss-licenses-plugin:0.12.0` works on AGP 8.7.3/Gradle 8.12.
- AboutLibraries spike uses 14.2.1, not 15.x, until AGP is upgraded.
- A generated lockfile changes when a direct release runtime dependency changes.
- Native inspector can list youtubedl-android library/ffmpeg AAR payloads without needing a full release build.
- Release workflow plan includes notice artifacts in checksums and release uploads.
