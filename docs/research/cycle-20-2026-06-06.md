# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 20
**Date:** 2026-06-06
**Repo state:** `main`, uncommitted Cycle 18/19 roadmap updates present, `versionCode 112`

## Executive Summary

Cycle 20 converted Cycle 19's tooling plan into two isolated compatibility spikes under `work/` outside the Aura worktree:

- `work/aura-oss-notice-spike` tested Google Play services OSS notices on Aura's current AGP 8.7.3 / Gradle 8.12 stack.
- `work/aura-aboutlibraries-spike` tested AboutLibraries Android plugin 14.2.1 on the same stack.

The Google OSS notices path is viable for the first implementation slice. It configures successfully after Gradle dependency verification metadata is reviewed, exposes variant-specific notice tasks, and generates release notice resources plus a dependency coordinate JSON without assembling an APK.

AboutLibraries 14.2.1 also configures after verification metadata is reviewed, but it is not the safer first slice based on this spike. Its release export tasks resolved classpaths during configuration, the compliance export logged Windows path errors for dependencies with colon-containing coordinates, and the generated library list only contained three Kotlin BOM entries without additional configuration. It may still be useful later for Compose-native UI, but Google OSS notices plus a custom lockfile/native packet is the better immediate plan.

## Findings

### Google OSS notices should be the first implementation path

Google OSS notices satisfies the immediate "generated in-app notice assets from release runtime dependencies" requirement on the current toolchain. It works without N-1 and produces concrete resources from the release dependency graph.

Implementation implication: apply the Google plugin, add the runtime dependency, wire Settings to launch the stock `OssLicensesMenuActivity` or parse/link the generated resources, and add the new Google plugin/runtime artifacts to Gradle dependency verification metadata with a carefully reviewed diff.

### Dependency verification must be treated as part of the feature

Both spikes failed first on Gradle dependency verification. That is good: Aura's checksum gate is doing its job. The actual implementation must include reviewed metadata updates and avoid broad accidental version churn when running `--write-verification-metadata`.

Implementation implication: use the narrowest command that resolves only the new plugin/runtime artifacts where possible, review `gradle/verification-metadata.xml`, and document the command in `docs/distribution/supply-chain.md`.

### Google output is not a lockfile or native compliance packet

The Google task generated dependency coordinates and raw license resources, but it does not provide a policy-reviewed lockfile or native payload inventory. It should be one layer in the notice lane, not the entire compliance strategy.

Implementation implication: follow Google OSS notices with a custom `docs/legal/dependency-notices.lock.json` or equivalent derived from `releaseRuntimeClasspath`, and a separate native payload inspector for youtubedl-android/FFmpeg.

### AboutLibraries 14.2.1 should stay secondary

AboutLibraries 14.2.1 is compatible enough to configure on AGP 8.7.3 / Gradle 8.12, which validates Cycle 19's version-gating note. However, its default output was incomplete for Aura and its compliance task had Windows path issues.

Implementation implication: do not choose AboutLibraries 14.2.1 as the first notice lane. Revisit only if the custom Compose UI requires it and allocate time to configure dependency collection correctly. Keep AboutLibraries 15.x deferred until N-1.
