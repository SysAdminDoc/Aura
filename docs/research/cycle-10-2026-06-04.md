# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 10
**Date:** 2026-06-04
**Repo state:** `main`, `4df134c`, `versionCode 112`

## Executive Summary

Cycle 10 focused on Android 17/API 37 platform readiness. Aura already shipped two Android 17-facing features through compileSdk-35-compatible raw strings/reflection, but the app is not yet ready to target API 37. The target bump is larger than a Gradle number change because Android 17 adds behavior gates for contacts, background audio, large screens, local network access, network security, and native/dynamic-code loading.

As of this pass, official Android release notes show Android 17 Beta 4.1 dated 2026-06-01, while the Android Developers Blog says Beta 3 reached Platform Stability on 2026-03-26. The API surface is locked enough for final compatibility planning, but Aura should still treat API 37 adoption as a tested release gate.

Top findings:

- P0: Aura is still on `compileSdk = 35` and `targetSdk = 35`, while Android 17 SDK work requires `compileSdk = 37`, `targetSdk = 37`, and at least Android Gradle Plugin 8.9.0-rc01. Aura currently uses AGP 8.7.3.
- P0: Contact ringtone selection still requests broad `READ_CONTACTS` and `WRITE_CONTACTS` together. Android 17 Contact Picker offers selected-contact read access without broad `READ_CONTACTS`, but ringtone writes may still require a just-in-time write permission or a documented fallback.
- P1: Android 17 ignores orientation/resizability/aspect restrictions for target-37 apps on `sw > 600dp` displays. Aura does not set explicit orientation restrictions, but local UI search found fixed two-column grids and no `WindowSizeClass`, `NavigationSuiteScaffold`, or list-detail adaptive layout usage.
- P1: Android 17 background audio hardening applies whether or not the app targets 37, and target 37 adds while-in-use foreground-service capability requirements. Aura uses a Media3 `MediaSessionService` and a `mediaPlayback` foreground service, but it needs Android 17 playback lifecycle tests.
- P1: Android 17 introduces `ACCESS_LOCAL_NETWORK` for target-37 apps, plus ECH and default Certificate Transparency behavior. Aura currently shows no local-network APIs, but it has a `ccmixter.org` cleartext exception and many remote providers that need a target-37 network compatibility preflight.
- P2: The Android 17 EyeDropper and Photo Picker 9:16 integrations are intentionally raw/reflection-based today. Once compileSdk 37 lands, the roadmap should replace those paths with direct API calls and keep fallback telemetry for un-updated OEM/system components.

External evidence reviewed:

- Android 17 SDK setup docs say Android 17 API work requires AGP 8.9.0-rc01 or higher, `compileSdk = 37`, and `targetSdk = 37` when opting into the new runtime behaviors.
- Android 17 release notes currently list Beta 4.1 on 2026-06-01. The Android Developers Blog states Beta 3 reached Platform Stability and that final compatibility testing can begin.
- Android 17 Contact Picker docs describe `Intent.ACTION_PICK_CONTACTS` as a privacy-preserving alternative to broad `READ_CONTACTS`; apps request specific fields and get selected-contact read access.
- Android 17 background audio hardening restricts background playback, focus, and volume interactions. Apps must have a visible activity or valid foreground service, and target-37 apps in the background need a foreground service with while-in-use capabilities. Invalid lifecycle calls can fail silently.
- Android 17 large-screen docs say apps targeting API 37 or higher have orientation, resizability, and aspect ratio restrictions ignored on displays whose smallest width is greater than 600dp.
- Android 17 target-SDK behavior docs add ECH support, mandatory `ACCESS_LOCAL_NETWORK` handling for LAN access, default Certificate Transparency, stricter static-final-field reflection behavior, Contacts Provider privacy changes, and safer native dynamic-code-loading constraints.
- Android local-network permission docs say target-37 apps are blocked by default from LAN access unless they use privacy-preserving pickers or declare/request `ACCESS_LOCAL_NETWORK`.
- Android Intent API reference confirms `ACTION_OPEN_EYE_DROPPER` and `EXTRA_COLOR` were added in API level 37.

## Findings

### API 37 is a release gate, not a narrow toolchain bump

Aura has already accrued Android 17 workarounds for EyeDropper and Photo Picker because the compile SDK remains at 35. That was a reasonable bridge, but direct API adoption now depends on a coordinated toolchain update: AGP, compileSdk, targetSdk, Kotlin metadata handling, baseline profile module settings, CI, and emulator coverage.

Planning implication: make the API 37 bump its own preflighted gate inside N-1. Do not fold it into a generic dependency bump without checking every target-37 behavior in this cycle note.

### Contact ringtone flow should minimize broad contact access

The current contact ringtone screen requests broad read and write contact permissions together. Android 17's Contact Picker can replace broad read access for the selection step by returning only user-selected contact data. However, setting `CUSTOM_RINGTONE` is still a write operation, so Aura needs to split the flow: picker-first selection, then request write access only when applying the ringtone if platform behavior requires it.

Planning implication: design an API 37+ flow that launches the system Contact Picker without broad `READ_CONTACTS`, reads only the selected record/session URI, and then applies ringtone changes with the narrowest possible permission story. If `WRITE_CONTACTS` remains required, it should be requested just in time with copy that explains the write, not bundled with read permission on screen entry.

### Large-screen behavior will expose portrait assumptions

Aura does not appear to rely on manifest orientation locks, so Android 17's removal of orientation/aspect restrictions is less dangerous than it would be for a portrait-locked app. The risk is still real: fixed two-column grids, bottom navigation only, and no window-size-class code can produce cramped or wasteful layouts on tablets, foldables, desktop-windowing, and connected displays.

Planning implication: add an Android 17 large-screen smoke pass before target 37 ships. This should cover landscape phone, tablet, foldable, freeform/desktop windowing, and split-screen. Failures should either be fixed in N-1/NX adaptive work or filed as target-37 blockers.

### Background audio needs Android 17 lifecycle evidence

Aura's audio service is already closer to the desired Android 17 shape than many apps: Media3 session service, media playback foreground-service type, media usage attributes, and task-removal cleanup. The remaining risk is evidence. Android 17 can silently fail playback/volume APIs if the app calls them from an invalid lifecycle state, so the release gate needs `adb dumpsys audio`/logcat checks and manual playback scenarios.

Planning implication: create a target-37 audio test script that starts preview playback, backgrounds the app, removes the task, denies/permits notification permission where relevant, and checks for `AudioHardening` logs or failed focus/playback behavior.

### Target-37 privacy and network changes need a preflight

Aura does not currently appear to use LAN discovery or sockets, so `ACCESS_LOCAL_NETWORK` should remain absent. That should become a testable invariant because future casting, local-device wallpaper transfer, or companion-app work could add LAN usage accidentally. Separately, target-37 network behavior changes such as ECH and default Certificate Transparency should be reviewed against the app's remote providers, especially the existing cleartext exception for `ccmixter.org`.

Planning implication: add a target-37 privacy/security compatibility preflight that scans for local-network APIs/permissions, dynamic loading of native libraries, private `MessageQueue` or static-final reflection, broad contact-provider queries without permissions, and provider endpoints affected by CT/ECH or cleartext exceptions.

### Raw/reflection Android 17 bridges need cleanup after compileSdk 37

The EyeDropper and Photo Picker bridges are useful because they shipped runtime behavior before compile SDK 37. Once compile SDK 37 lands, keeping the raw strings/reflection as the main path raises maintenance risk and hides compile-time breakage. Fallbacks can stay for defensive logging, but the primary code path should use the platform symbols.

Planning implication: pair the API 37 bump with direct `Intent.ACTION_OPEN_EYE_DROPPER`, `Intent.EXTRA_COLOR`, and direct `PhotoPickerUiCustomizationParams` integration, plus telemetry/logging for systems where OEM/system components are missing or reflection fallback still triggers.

## Open Questions

- Should API 37 target adoption be paired with AGP 9.x from the existing N-1 plan, or first land on the documented minimum AGP 8.9.0-rc01+ to reduce blast radius?
- Can Android 17 Contact Picker return enough stable contact identity for `CUSTOM_RINGTONE` updates without broad `READ_CONTACTS`, or does Aura need a selected-contact lookup/write fallback?
- Should Aura keep broad `WRITE_CONTACTS` in the manifest for older devices, or gate it with `maxSdkVersion` once API 37+ Contact Picker behavior is proven?
- Which Android 17 emulator/device profiles should become the minimum release lab: Pixel phone, tablet, foldable, desktop-windowing, and one Android 16 regression device?
- Should future companion/casting work explicitly require an `ACCESS_LOCAL_NETWORK` design review before any LAN API lands?
