# Cycle 157 research - background work receipts

## Goal

Persist lightweight last-run receipts for Aura's scheduled background work so
Settings diagnostics can show more than current WorkInfo state.

## Local evidence

- Cycle 156 added `Settings` > `Diagnostics` > `Background work` with one row
  per unique work name, WorkInfo state counts, max run attempts, and
  metered/Data Saver status.
- `AutoWallpaperWorker`, `DailyWallpaperWorker`, `WeatherUpdateWorker`, and
  `AuraOriginalsDownloader` are Hilt workers and can receive a singleton
  receipt store.
- `RotationTriggerService` uses `AutoWallpaperWorker` for the
  `rotation_trigger_oneshot` unique work, so it needs an input-data receipt key
  to avoid writing trigger receipts under the periodic `auto_wallpaper` row.

## Implementation decision

Added a SharedPreferences-backed `BackgroundWorkReceiptStore` that records:

- last success UTC;
- last failure UTC;
- last error class;
- last result (`success`, `retry`, or `failure`);
- last deferral reason.

The four worker classes now record receipts on success, retry, and failure
paths. Rotation-trigger one-shots pass their unique work name through
`AutoWallpaperWorker.RECEIPT_WORK_NAME_KEY`, so Settings can keep trigger
receipts separate from periodic auto-wallpaper receipts.

## Remaining work

- Replace generic retry reasons with sharper user-actionable platform causes
  where workers can identify them directly.
- Merge the persisted receipt snapshot into the copied support bundle if the
  support flow should include live local worker state.
- Consider a future receipt clear/reset action if stale receipts become noisy
  during support triage.
