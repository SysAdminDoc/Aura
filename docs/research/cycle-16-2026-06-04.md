# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 16
**Date:** 2026-06-04
**Repo state:** `main`, `5622fb6`, `versionCode 112`

## Executive Summary

Cycle 16 focused on local data integrity, Room migrations, backup/restore behavior, and collection/favorites import-export resilience. Aura already has a serious data model: favorites, downloads, search history, wallpaper cache, wallpaper history, collections, collection items, offline paths, provider provenance, and public share-token imports. These are user-facing durability surfaces, so upgrade and restore correctness matter as much as initial feature behavior.

Top findings:

- P0: Collection share links appear broken under the tracked RTDB rules. `CollectionExporter` writes and reads `shared_collections/{token}/payload`, while `database.rules.json` defines rules for `collection_shares/{token}`. Firebase RTDB denies access by default when no `.read` or `.write` rule grants access at or above a path.
- P0: Room is at version 14 with manual migrations from 1 to 14, but exported schema JSON exists only for versions 9 through 14 and the tracked migration androidTest validates only a hand-built 8 -> 9 case.
- P1: The main `freevibe.db` is eligible for backup/transfer by default, while volatile WAL/SHM/journal files are excluded. That may preserve favorites and collections, but restored `offlinePath`, `localPath`, cached provider metadata, stale download records, and missing media files need reconciliation.
- P1: Favorites import is relatively well bounded, but collection import has split behavior: URI imports cap file bytes at 512 KiB, while token imports read a database payload string and then parse it without an equivalent local payload-size check.
- P1: Collection import creates the collection first and adds valid items one by one. A database failure mid-import can leave a partial imported collection unless a transaction or cleanup path covers it.
- P2: Export formats are versioned at `1`, but there is no documented export-format compatibility policy for future favorites/collection schema changes, source capability fields, deleted-source states, or provenance metadata.

- `app/build.gradle.kts` sets Room schema output to `$projectDir/schemas` and adds `androidTest` schema assets from the same folder.
- Tracked schema files exist for database versions 9, 10, 11, 12, 13, and 14. Versions 1 through 8 are not present in `app/schemas`.
- `DatabaseMigrations.ALL_MIGRATIONS` includes `MIGRATION_1_2` through `MIGRATION_13_14`.
- `AppModule.provideDatabase()` uses `Room.databaseBuilder(..., "freevibe.db")`, adds all migrations, enables foreign keys in `onOpen`, and does not call destructive migration fallback.
- `DatabaseMigrationTest` uses `MigrationTestHelper`, but currently validates only `MIGRATION_8_9`. It manually creates a version 8 schema instead of loading a version 8 exported Room schema.
- Source-aware identity changes already landed:
  - v11 -> v12: favorites primary key changed to `id + source + type`.
  - v12 -> v13: collection items primary key changed to `collectionId + wallpaperId + source`.
  - v13 -> v14: wallpaper cache primary key changed to `id + source + cacheKey`.
- `backup_rules.xml` and `data_extraction_rules.xml` exclude `freevibe.db-journal`, `freevibe.db-shm`, and `freevibe.db-wal`, but not the main `freevibe.db` database.
- `backup_rules.xml` and `data_extraction_rules.xml` exclude DataStore preferences and `crash.log`, but not the fallback community identity shared preference `aura_community_identity` noted in Cycle 4/12.
- `FavoritesExporter` caps imported JSON at 2,000,000 chars, caps item count at 5,000, supports a legacy list format, rejects future versions above the current format, validates source/type, caps text/URL field lengths, and requires HTTPS URLs.
- `CollectionExporter` caps URI import bytes at 512 KiB, caps collection import/export items at 250, requires HTTPS `fullUrl`, caps collection names at 80 chars, and accepts only format version 1.
- `CollectionExporter.importFromTokenOrLink()` reads `db.child("shared_collections").child(token).child("payload")`; `publishPayload()` writes to the same `shared_collections` path.
- `database.rules.json` defines `collection_shares/{token}`, not `shared_collections/{token}`, and does not validate payload structure, item count, payload length, creator UID, or created-at fields under the client-used path.
- `CollectionExporterTest` covers token parsing and name sanitization, but not JSON payload byte caps, malformed payloads, disallowed URLs, unsupported sources, duplicate items, transactional import behavior, or RTDB path/rules alignment.

External evidence reviewed:

- Android Room migration docs say migrations are complex, incorrect migrations can crash apps, and migration tests should use exported schemas stored in version control.
- `MigrationTestHelper` is designed to create lower database versions and run migrations/validation using exported schemas.
- Android Auto Backup docs say backup rules can include or exclude `file`, `database`, and `sharedpref` domains; for Android 12+ `data-extraction-rules` separate cloud backup and device transfer; excludes take precedence over includes.
- Android app-specific file docs say cache files can be removed by the system and apps should maintain their own cache cleanup.
- Firebase RTDB rules docs say access is denied by default when no `.read` or `.write` rule is specified at or above a path, and `.validate` rules should enforce data structure and content.

## Findings

### Collection share links need backend path alignment

The code and rules disagree about the public share-token path. The app reads and writes `shared_collections`, while the tracked rules grant access under `collection_shares`. Because RTDB access is denied by default, a production rules deploy using the tracked file should reject both publish and import attempts for `shared_collections` unless another untracked ruleset exists.

Planning implication: align the path name in code and rules, then add emulator tests that prove publish, public read-by-token, owner/admin overwrite/delete, malformed payload rejection, and oversized payload rejection. This should be treated as P0 because collection sharing is listed as shipped.

### Room migrations need whole-graph evidence

The migration list covers every step from v1 to v14, which is good. The evidence gap is testing and schema history. Only versions 9 through 14 have exported schemas, and the androidTest currently checks one hand-built version 8 migration. That means the most risky old installs are not represented by schema artifacts, and the most recent source-aware identity migrations are not covered by data-preservation tests.

Planning implication: add a migration harness that exercises every supported entry version to current, including representative rows for favorites, downloads, history, cache, collections, and duplicate raw IDs across providers.

### Backup/restore can preserve records whose files no longer exist

The main Room database is eligible for backup, but cache, offline media, generated images, and app-specific file paths may not restore the same way. `FavoriteEntity.offlinePath` and `DownloadEntity.localPath` can point to files that are absent after cloud restore, device transfer, cache clear, or storage cleanup. That is not necessarily a privacy problem if disclosed, but it is a data-integrity problem if UI shows broken offline/downloaded states.

Planning implication: add a restore reconciliation job that verifies every path-backed record, clears or repairs missing local paths, preserves remote provenance, and reports "remote-only" or "file missing" state instead of failing later in apply/share/play flows.

### Import needs one contract across file, deep link, and token paths

Favorites import has size, version, source/type, URL, and field-length limits. Collection import has some of those limits, but token imports bypass the URI byte reader and rely on RTDB payload shape. Even generated share payloads are capped by item count, but imports should be robust against manually written or corrupted RTDB nodes.

Planning implication: route file and token payloads through one capped parser, and validate collection fields as strictly as favorites: source enum, text length, URL length, HTTPS for thumbnail/full/source page where applicable, duplicate identity handling, item count, and payload size.

### Collection import should be transactional

`importJson()` creates a collection row, then inserts items individually. If a database error occurs after the collection is created, the UI can show an empty or partial "Imported" collection. Since collections are user-visible durable data, import should either commit the whole collection or leave no imported rows.

Planning implication: add DAO transaction support for collection import or perform cleanup on failure. Tests should inject an insert failure and confirm no partial collection remains.

## Verification Targets

- Firebase emulator tests prove collection share publish/import uses the same rules path and rejects unauthenticated writes, malformed payloads, oversized payloads, and unauthorized overwrites.
- Room migration tests cover every supported start version to v14 and preserve source-aware duplicate identities across favorites, collections, and wallpaper cache.
- CI or release preflight fails if `FreeVibeDatabase.version` changes without a new schema JSON and migration test update.
- Backup/restore smoke run seeds favorites, downloads, offline paths, collections, search history, weather prefs, DataStore keys, and identity prefs, then verifies the documented include/exclude/reconcile result.
- Import fuzz tests cover huge JSON, unsupported versions, malformed fields, unsafe URLs, duplicate items, unknown providers, empty payloads, and mid-transaction failures.
