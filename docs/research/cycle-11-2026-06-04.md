# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 11
**Date:** 2026-06-04
**Repo state:** `main`, `c90c18c`, `versionCode 112`

## Executive Summary

Cycle 11 focused on Android and Play sensitive-permission posture, with emphasis on ringtone/audio features that combine special app access, microphone recording, location-derived weather effects, contacts, notifications, foreground services, and exported automation.

Aura already uses several just-in-time permission patterns, but the planning gap is store-facing evidence. Google Play now treats restricted permissions and sensitive APIs as minimum-scope, incrementally requested surfaces that must be necessary for promoted core functionality, disclosed consistently in the listing, privacy policy, Data safety form, and any foreground-service declarations. Aura does not yet have a single permission inventory tying manifest entries to feature copy, data types, denial paths, retention, and release preflight.

Top findings:

- P0: Aura declares `WRITE_SETTINGS`, `RECORD_AUDIO`, `ACCESS_COARSE_LOCATION`, `READ_CONTACTS`, `WRITE_CONTACTS`, `POST_NOTIFICATIONS`, two foreground-service type permissions, `SET_ALARM`, and legacy `WRITE_EXTERNAL_STORAGE`, but no docs-side permission/data-safety matrix was found.
- P0: `WRITE_SETTINGS` is correctly checked before default ringtone/notification/alarm writes, but every special-access launch needs a documented rationale, return validation, and fallback for devices without the exact settings activity.
- P1: `SET_ALARM` is declared although local search found no `AlarmClock`, `ACTION_SET_ALARM`, or `AlarmManager` code path. It is a normal permission, but it still violates the "declared only for current features" release discipline unless removed or justified.
- P1: Community sound recording requests `RECORD_AUDIO` from a user action and keeps recordings in cache, but the roadmap needs explicit local-until-upload/public-if-uploaded disclosure, stale-temp cleanup, and Data safety rows for voice/sound recordings and other audio files.
- P1: Weather effects use only coarse location, but `WeatherUpdateWorker` sends latitude/longitude to Open-Meteo and stores `location_lat`/`location_lon` in `freevibe_weather_wp`; disabling weather cancels work but no clear stored-location wipe was found.
- P1: Aura has `mediaPlayback` and `specialUse` foreground services. Play requires service-type declarations with use-case descriptions, user impact, and demonstration videos for Android 14+ target updates.

## Current State

Local evidence reviewed:

- `AndroidManifest.xml` declares `WRITE_SETTINGS`, `com.android.alarm.permission.SET_ALARM`, `RECORD_AUDIO`, `INTERNET`, `ACCESS_NETWORK_STATE`, `WRITE_EXTERNAL_STORAGE` with `maxSdkVersion=28`, `RECEIVE_BOOT_COMPLETED`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, `FOREGROUND_SERVICE_SPECIAL_USE`, `POST_NOTIFICATIONS`, `ACCESS_COARSE_LOCATION`, `READ_CONTACTS`, and `WRITE_CONTACTS`.
- `SoundApplier.canWriteSettings()` gates ringtone writes with `Settings.System.canWrite(context)`, and `requestWriteSettings()` launches `Settings.ACTION_MANAGE_WRITE_SETTINGS` with a package URI.
- `SoundApplier.downloadAndApply()` and `applyFromLocalFile()` throw if `WRITE_SETTINGS` is missing, save audio to MediaStore ringtone/notification/alarm collections, then call `RingtoneManager.setActualDefaultRingtoneUri()`.
- `SoundDetailScreen.kt` and `SoundsScreen.kt` disable default-sound apply actions when `canWriteSettings()` is false and route users to the system settings grant flow.
- `SoundsScreen.kt` requests `RECORD_AUDIO` only when the user starts recording community audio. `CommunityAudioRecorder.kt` records AAC/M4A microphone audio to `cacheDir/sounds/community_recordings/` with a 60-second maximum, returns a FileProvider URI on stop, and deletes the active temp file on cancel.
- `WeatherUpdateWorker.kt` checks fine and coarse location but the manifest only declares coarse. It uses the network provider when coarse is available, calls Open-Meteo with the last-known latitude/longitude, and stores weather values plus `location_lat`, `location_lon`, and `location_present` in `freevibe_weather_wp`.
- `SettingsScreen.kt` requests `POST_NOTIFICATIONS` before enabling daily wallpaper notifications and requests `ACCESS_COARSE_LOCATION` before enabling weather effects. Disabling weather cancels the worker, but this pass did not find an explicit wipe of persisted location coordinates.
- `RotationTriggerService` runs a `specialUse` foreground service for per-unlock and screen-off wallpaper triggers and posts a low-priority "Aura - wallpaper triggers" notification.
- `AudioPlaybackService` is exported as a Media3 `MediaSessionService` with `foregroundServiceType="mediaPlayback"`.
- `TaskerActionReceiver` is exported and accepts rotate/shuffle actions. Existing roadmap Cycle 4 already tracks opt-in, rate limiting, and diagnostics for that automation surface.
- `docs/privacy` was not present. `fastlane/metadata/android/en-US/full_description.txt` promotes YouTube sounds, weather, BYO AI key, contact ringtones, Tasker, and community uploads while also claiming no ads, tracking, account, or subscription.
- `backup_rules.xml` and `data_extraction_rules.xml` exclude `freevibe_weather_wp.xml` from backup/transfer, but Cycle 4 already noted other identity/community data backup questions.

External evidence reviewed:

- Google Play's permissions/sensitive-API policy says sensitive permissions must be necessary for promoted current features, requested incrementally, used only for consented purposes, and not declared for undisclosed, unimplemented, or disallowed purposes.
- The same Play policy previews an October 28, 2026 contacts-permission policy that will push apps that do not need broad contact access toward the Android Contact Picker.
- Google Play's personal and sensitive user data policy includes phonebook/contacts, device location, microphone, and other sensitive device or usage data.
- Google Play Data safety docs include approximate location, contacts, voice/sound recordings, music files, other audio files, crash logs, diagnostics, device IDs, app interactions, and user-generated content as data types that may need disclosure depending on collection and sharing.
- Android runtime permission docs recommend requesting permissions only when needed, after a user action, with an explanation when the permission is required.
- Android location docs emphasize minimum scope and users' ability to grant approximate rather than precise location.
- Android notification docs say Android 13+ requires runtime notification permission for non-exempt notifications; foreground services can launch without `POST_NOTIFICATIONS`, but the notification drawer behavior changes if permission is denied.
- Android foreground-service docs define `mediaPlayback` and `specialUse` service types, and Play Console foreground-service declarations require descriptions, user-impact explanations, and videos for declared types.
- Android `Settings.System.canWrite()` docs confirm apps on API 23+ need `WRITE_SETTINGS` in the manifest plus a specific user grant through `Settings.ACTION_MANAGE_WRITE_SETTINGS`.
- Android `Settings.ACTION_MANAGE_WRITE_SETTINGS` docs note a matching settings activity may not exist and callers should guard against that.
- Android `SET_ALARM` permission docs describe it as allowing an app to broadcast an intent to set an alarm for the user. Local source search found no matching alarm-setting flow.

## Findings

### Aura needs a permission declaration packet before store submission

The manifest contains several user-sensitive or policy-relevant surfaces, but the project does not yet have one doc that maps each permission to a current feature, user action, disclosure copy, Data safety row, denial behavior, retention, and store declaration. Cycle 4 and Cycle 8 already identified privacy policy and app-content gaps; Cycle 11 narrows that into a release-gating permission ledger.

Planning implication: add a permission/data-safety packet that is generated or checked from the manifest. New permissions should fail release preflight until the row exists and the listing/privacy/Data safety claims are consistent.

### `WRITE_SETTINGS` is a special-access flow, not just a disabled button

Aura correctly prevents ringtone/notification/alarm writes when `Settings.System.canWrite()` is false, and the UI points users to the system settings grant. Android docs add two details the roadmap should capture: the user must specifically grant this capability, and the settings activity may not exist on some devices. The current docs also need to explain why Aura modifies system settings and how the user can revoke it.

Planning implication: make default-sound apply flows testable across grant, deny, revoke, and no-settings-activity scenarios. The special access should be disclosed in app copy and the store permission packet without overstating what data is collected.

### The `SET_ALARM` declaration is currently unsupported by source evidence

`SET_ALARM` is a normal permission rather than dangerous, but it still declares a user-facing capability that Aura does not appear to use. Local search did not find `AlarmClock`, `ACTION_SET_ALARM`, or `AlarmManager` code paths. If the alarm sound apply path only writes default alarm tones through `RingtoneManager`, `SET_ALARM` should likely be removed.

Planning implication: treat dormant manifest entries as release blockers. Remove `SET_ALARM` unless an actual user-initiated alarm-setting feature is implemented and documented.

### Community recording needs retention and publication copy

The microphone request is appropriately triggered from the recording action, and temporary files live in cache. The missing piece is product and policy evidence: users should see that recording stays local until they upload, uploaded sounds may become public community content, stale cached recordings are cleaned up, and deletion/reporting behavior is defined.

Planning implication: pair the community upload flow with a microphone/audio retention checklist and Data safety rows for voice/sound recordings, other audio files, user-generated content, and any backend sharing.

### Weather location is narrow but should clear and disclose coordinates

Aura requests coarse location, not fine/background location, which matches minimum-scope guidance. However, `WeatherUpdateWorker` still sends and stores latitude/longitude. Even if the Android permission is approximate, the privacy packet should say exactly what service receives location, what precision is used, and what happens when weather effects are disabled.

Planning implication: disabling weather should clear stored location/weather state, and the release preflight should verify no fine/background location or backup leakage was introduced.

### Foreground-service declarations need release evidence

Aura declares both media playback and special-use foreground services. This is plausible for audio preview and wallpaper rotation triggers, but Play target-34+ updates require service-type descriptions, user-impact explanations, and demo videos. Notification permission denial also changes the visibility of foreground-service notifications, which should be tested.

Planning implication: maintain a foreground-service declaration packet tied to manifest services, channel names/copy, settings toggles, and demo-video scripts.

## Verification Targets

- Static permission preflight compares the merged manifest against a docs ledger and fails on missing rows.
- Manual permission-denial lab covers `WRITE_SETTINGS`, microphone, coarse location, notification permission, contacts, and foreground-service notification states.
- Store packet review confirms Play listing, privacy policy, Data safety form, foreground-service declarations, and fastlane metadata do not contradict each other.
- Cache/prefs inspection confirms discarded recordings and disabled weather state do not retain unnecessary sensitive data.
- Play/alternate-store release checklist includes evidence for each sensitive permission and special app access.
