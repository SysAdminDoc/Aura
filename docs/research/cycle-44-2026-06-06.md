# Cycle 44 Research: Pixabay Video Request Cache And Backoff

## Goal

Close the remaining Pixabay runtime-policy gap by giving Pixabay video metadata
the same 24-hour request-cache and 429 backoff behavior already added for
Pixabay photo metadata.

## Source Evidence

- [Pixabay API documentation](https://pixabay.com/api/docs/) states that
  requests must be cached for 24 hours.
- The same documentation describes rate-limit headers including
  `X-RateLimit-Reset` and 429 behavior for exceeded API limits.

## Local Evidence

- `WallpaperRepository.getPixabay()` already serves fresh cached photo metadata
  before remote calls and uses stale rows during active rate-limit backoff.
- `VideoWallpapersViewModel` still called `PixabayApi.searchVideos()` directly
  and only cached resolved stream URLs in memory, so app restarts could repeat
  the same video metadata request inside Pixabay's 24-hour request-cache window.
- The existing video path already had a provider-enabled guard before bundled
  key reads, so the missing behavior was cache/backoff rather than source
  disablement.

## Decision

Use a small app-private `SharedPreferences` cache for Pixabay video metadata.
That keeps the guard durable across app restarts without adding a Room migration
for UI-only video browsing rows. Keep stream URLs paired with cached metadata so
cached video rows remain directly applyable.

## Implementation Notes

- Added `PixabayVideoFetchSpec`, cache key, mapping, encode/decode, freshness,
  and rate-limit helper functions in `VideoWallpapersViewModel.kt`.
- Pixabay video loads now check a 24-hour fresh cache before `searchVideos()`.
- Successful non-empty video metadata responses are cached with their resolved
  stream URLs.
- 429 responses parse `Retry-After` first, then `X-RateLimit-Reset`, and store
  the active backoff window in app-private preferences.
- During active backoff, the video feed uses stale cached rows when available
  and otherwise marks Pixabay degraded without retrying.
- `ProviderDisclosure.kt` and `docs/legal/provider-runtime-controls.md` now mark
  Pixabay runtime controls covered because photo and video metadata paths both
  enforce the provider request-cache/backoff policy.

## Verification Plan

- Focused video wallpaper helper tests cover Pixabay fetch spec selection,
  metadata mapping, cache round trip, expired-vs-stale reads, and 429 header
  parsing.
- Provider disclosure tests verify Pixabay no longer carries an outdated
  partial runtime-control follow-up.
- Release-compliance Python checks remain unchanged and should still pass.
