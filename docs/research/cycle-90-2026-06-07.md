# Cycle 90 - Upload Deletion Execution Receipt

## Scope

Add a redacted receipt gate for public upload deletion execution after a clean
account-deletion upload handoff plan has no blocked rows.

## Sources

- Firebase Storage delete files:
  https://firebase.google.com/docs/storage/android/delete-files
- Firebase Realtime Database delete data:
  https://firebase.google.com/docs/database/android/read-and-write
- Existing upload handoff plan:
  `tools/community_account_deletion_upload_plan.py`

## Local Evidence

- Cycle 87 enumerates owned sound and wallpaper uploads and blocks rows with
  missing or mismatched Storage handles.
- The repo still lacked a normalized evidence receipt after the owner/admin
  upload deletion workflow deletes Storage objects, removes public metadata,
  removes owner indexes, and writes private tombstones.
- A receipt tool should validate private evidence after the workflow completes;
  it should not delete public uploads directly or expose raw Storage paths.

## Implementation

- Added `tools/community_account_deletion_upload_execution_receipt.py`.
- The receipt builder validates a ready upload handoff plan, rejects blocked
  plans, requires every candidate to have matching private execution evidence,
  and requires each row to prove Storage deletion, metadata deletion,
  owner-index deletion, and tombstone write completion.
- The emitted receipt contains counts and hashes while omitting full UIDs, raw
  upload IDs, RTDB paths, Storage paths, project ID, credentials, command
  output, and tokens.
- Added `validate_upload_execution_receipt()` for future downstream private
  deletion tooling.
- Added `test/tools/community_account_deletion_upload_execution_receipt_test.py`
  for the redacted happy path plus blocked plan, missing row, incomplete delete,
  and path mismatch rejection cases.
- Wired the tool into Firebase backend CI change detection.
- Updated support, policy, backend runbook, upload deletion runbook, roadmap,
  changelog, completed ledger, and loop state docs.
