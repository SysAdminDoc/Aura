# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 4
**Date:** 2026-06-04
**Repo state:** `main`, `3c3bc96`, `v6.31.1-10-g3c3bc96`, `versionCode 112`

## Executive Summary

Cycle 4 focused on privacy, permission minimization, backup behavior, and data-safety readiness. Aura's open-source/no-ads positioning is strong, but the app now handles enough user-controlled and sensitive surfaces that trust needs to be encoded as a product contract, not just inferred from source.

Top findings:

- P0: Aura needs a privacy policy and Data safety/source-of-truth matrix before Play, Izzy, or broad Obtainium promotion. Play policy treats contacts, location, microphone, user-provided audio/photos, crash logs, diagnostics, user IDs, and other user-generated content as data that must be accurately disclosed.
- P0: Community uploads are public-readable in RTDB and Firebase Storage download URLs are stored in public metadata. Aura needs a community data lifecycle: what is public, who owns it, how deletion works, what identifiers are retained, and how reports/removal requests are handled.
- P1: Per-contact ringtone assignment currently requests broad `READ_CONTACTS` and `WRITE_CONTACTS` on screen entry. Android 17's Contact Picker offers a narrower read path and should become the default selection flow.
- P1: Backup rules exclude several sensitive prefs and `crash.log`, but `allowBackup=true` still permits other app state to move through cloud/device transfer. The rules need a documented include/exclude inventory for API keys, local identity, favorites, cached source metadata, and generated/downloaded content.
- P1: Weather effects use coarse location permission, but the worker sends latitude/longitude to Open-Meteo and stores lat/lon in SharedPreferences. This is reasonable for a weather feature, but it needs just-in-time disclosure, retention/clearing behavior, and a city/coarse precision stance.
- P2: The exported Tasker/MacroDroid receiver is useful but unauthenticated. It should be opt-in, documented, and rate-limited/auditable so external apps cannot silently churn wallpaper rotations.

## Current State

Local evidence reviewed:

- `AndroidManifest.xml` declares `SET_WALLPAPER`, `WRITE_SETTINGS`, `SET_ALARM`, `RECORD_AUDIO`, `INTERNET`, `ACCESS_NETWORK_STATE`, API-28-limited `WRITE_EXTERNAL_STORAGE`, `RECEIVE_BOOT_COMPLETED`, foreground-service permissions, `POST_NOTIFICATIONS`, `ACCESS_COARSE_LOCATION`, `READ_CONTACTS`, and `WRITE_CONTACTS`.
- `AndroidManifest.xml` sets `android:allowBackup="true"`, `android:fullBackupContent="@xml/backup_rules"`, and `android:dataExtractionRules="@xml/data_extraction_rules"`.
- `backup_rules.xml` and `data_extraction_rules.xml` exclude dark-mode/live-wallpaper/weather shared prefs, datastore `freevibe_prefs.preferences_pb`, crash log, and Room WAL/journal sidecars. They do not exclude the main `freevibe.db` database or `aura_community_identity` shared preferences.
- `CommunityIdentityProvider.kt` creates anonymous Firebase identities when available, stores a local fallback UUID in `aura_community_identity`, and still exposes a legacy `Settings.Secure.ANDROID_ID` value through `knownIdentityIds()`.
- `UploadRepository.kt` uploads user-provided audio files to Firebase Storage, stores public RTDB metadata including `downloadUrl`, `uploaderId`, `uploaderLabel`, file type, original file name, tags, and category, and exposes public community-upload reads.
- `database.rules.json` allows public reads for votes, moderation state, community sounds, community wallpapers, and collection shares. Authenticated users can create public community metadata; Custom-Claim admins can moderate.
- `ContactPickerScreen.kt` immediately launches a `READ_CONTACTS` + `WRITE_CONTACTS` permission request when the screen opens if permissions are missing, then searches all contacts locally.
- `WeatherUpdateWorker.kt` reads last-known coarse/fine location if granted, calls Open-Meteo with latitude/longitude, and stores weather effect, wind, temperature, `location_lat`, and `location_lon` in `freevibe_weather_wp`.
- `CrashDiagnosticsCollector.kt` builds a local-only diagnostics bundle with app/device/source context and a sanitized crash-log tail. Settings copy/share is explicit and `docs/support/crash-diagnostics.md` documents that nothing uploads automatically.
- `TaskerActionReceiver.kt` is exported and accepts `com.freevibe.action.ROTATE_NOW` / `SHUFFLE_NOW` from external automation tools without a custom permission.
- Search found no checked-in privacy-policy or data-safety source-of-truth document.

External evidence reviewed:

- Google Play User Data policy requires transparent disclosure, runtime permission requests where available, secure transmission, no sale of personal/sensitive user data, and an app privacy policy even for apps that do not access personal/sensitive data.
- Google Play's Data safety guidance classifies approximate location, contacts, photos/videos, voice/sound recordings, other audio files, files/docs, other user-generated content, app interactions, crash logs, diagnostics, and device/other IDs as data types that may need disclosure depending on collection/sharing behavior.
- Google Play prominent-disclosure guidance recommends explaining unexpected personal/sensitive data use immediately before permission or sensitive capability access, with a decline path and graceful degradation.
- Android runtime-permission docs require dangerous permissions to be requested at runtime and recommend explaining feature impact when users deny permissions.
- Android location docs recommend requesting only coarse location when sufficient. Weather effects appear to need only approximate location.
- Android 17 Contact Picker gives apps selected-contact read access without broad address-book access and can be tested on Android 17 using the system picker path.
- Android Auto Backup docs say apps targeting Android 12+ use `data-extraction-rules`, while Android 11 and lower still need `fullBackupContent`; include/exclude rules should be explicit for sensitive state.
- Firebase Realtime Database rules are server-enforced and should combine authentication, authorization, and validation. App Check remains a separate abuse-control layer already covered by Cycle 1.
- Android/Play foreground-service docs require clear `specialUse` declarations and Play Console descriptions/videos for Android 14+ foreground-service types.

## Findings

### Privacy and Data safety need a single source of truth

Aura can truthfully say it avoids ads and automatic crash analytics, but it cannot treat privacy disclosure as optional. The manifest and code touch location, contacts, microphone recording, user-provided audio/photos, Firebase anonymous IDs, public community metadata, crash diagnostics, API keys, and local preferences.

Planning implication: add `docs/privacy/data-safety.md` plus an in-app privacy screen. It should map every manifest permission, SDK, local store, and network destination to data type, purpose, user action, sharing/collection status, retention, deletion path, and Data safety answer.

### Community data is public by design but not documented as public

Community metadata and public Firebase Storage URLs are readable by anyone. That may be acceptable for an open community catalog, but users need clear upload-time disclosure and deletion/report paths. The current audio upload metadata includes original file names and uploader labels. The rules also use `uploaderUid` in write ownership checks while the sound upload code writes `uploaderId`, which should be audited before promising self-service edits/deletion.

Planning implication: make uploads explicitly public, minimize metadata, normalize owner fields, add deletion/retention workflow, and document what remains visible after moderation or removal.

### Contact access can be narrowed

Aura's per-contact ringtone feature currently requests read/write access to the address book as soon as the contact picker screen opens. Android 17 now has a system Contact Picker that can return only selected contact data. Aura likely still needs a write path to set custom ringtone values, but broad read access should not be the default on API 37+.

Planning implication: build an API 37+ picker-first path and hold broad contacts permission behind the final write operation or a clear fallback for older devices.

### Backup configuration needs an inventory, not just excludes

The backup files correctly exclude DataStore prefs and crash logs, but they leave other state eligible by default. That can be right for favorites, collections, and selected wallpapers, but it should be intentional. `aura_community_identity` and `freevibe.db` need an explicit decision because they can include IDs, source URLs, favorites, cached content metadata, and user-created state.

Planning implication: create a backup matrix with include/exclude decisions and tests that inspect generated APK XML plus local file names after a smoke run.

### Weather location should be just-in-time and self-clearing

Weather effects request only coarse location in Settings, which matches Android guidance for approximate-location use cases. But the worker stores lat/lon and sends them to Open-Meteo. That is expected for weather but should be disclosed at the exact toggle, rounded where possible, cleared when the toggle is turned off, and absent from backups.

Planning implication: add a weather privacy contract: coarse-only, no background-location permission, no precise request, clear stored lat/lon on disable, and document Open-Meteo as a weather data destination.

### Exported automation needs a consent boundary

The Tasker receiver intentionally exposes rotation intents to other apps. Because it has no custom permission, any app can send those broadcasts. The effect is constrained to wallpaper rotation, but repeated external triggers can still consume network/battery and surprise users.

Planning implication: gate external automation behind a Settings toggle, rate-limit incoming broadcasts, show last external trigger in diagnostics, and document the public intent contract.

## Roadmap Queue

- [ ] P0 - Privacy policy and Data safety source-of-truth matrix
  - Why: Aura handles contacts, coarse location, microphone recordings, user-provided media, Firebase anonymous IDs, public community metadata, crash diagnostics, local preferences, and third-party provider requests. Play requires a privacy policy and accurate Data safety disclosures.
  - Evidence: manifest permissions; `CommunityIdentityProvider.kt`; community upload repositories; `CrashDiagnosticsCollector.kt`; Google Play User Data/Data safety/prominent-disclosure guidance.
  - Touches: `docs/privacy/data-safety.md`, Settings privacy screen, README, release checklist, issue templates, distribution docs.
  - Acceptance: every permission/SDK/network destination/local store has data type, purpose, collection/sharing status, retention, deletion path, and Data safety answer; in-app privacy screen links the policy and local-only diagnostics statement; release checklist requires review on manifest/dependency changes.
  - Verify: static permission inventory matches matrix; Data safety rows cover location/contacts/audio/photos/user content/crash logs/diagnostics/device IDs; no release can ship with unchecked privacy matrix diff.

- [ ] P0 - Community upload public-data lifecycle and deletion workflow
  - Why: Community sounds/wallpapers and collection shares are public-readable, and upload metadata includes Firebase download URLs, uploader labels/IDs, file names, tags, and categories. Users need to know uploads are public and need removal controls.
  - Evidence: `database.rules.json` public reads; `UploadRepository.kt` public download URL metadata; Firebase rules guidance; Cycle 1 report queue and Cycle 3 takedown items.
  - Touches: upload dialogs, RTDB rules, Storage metadata, creator profile repository, report queue, `docs/privacy/community-data.md`.
  - Acceptance: upload flow says content and metadata become public; metadata excludes unnecessary original filenames or clearly justifies them; owner field names are consistent; users can delete their uploads or request removal; admin moderation hides public catalog entries and has retention notes.
  - Verify: Firebase rules tests for owner delete/admin hide/public read; upload/delete manual pass; public catalog no longer exposes unneeded metadata; removal path documented in privacy policy.

- [ ] P1 - Android 17 Contact Picker and contacts-permission minimization
  - Why: Per-contact ringtone assignment requests broad contacts read/write permissions immediately on screen entry. Android 17 provides a picker that gives selected-contact read access without broad address-book access.
  - Evidence: `ContactPickerScreen.kt` immediate `READ_CONTACTS`/`WRITE_CONTACTS` launcher; Android 17 Contact Picker docs; Play User Data contact restrictions.
  - Touches: `ContactPickerScreen`, `ContactRingtoneService`, permission copy, Settings privacy screen, API 37 test plan.
  - Acceptance: API 37+ uses system Contact Picker for contact selection; broad read contacts permission is not requested before the user selects a contact; write permission is requested only when needed to set the ringtone; older devices retain a just-in-time fallback.
  - Verify: API 37 picker flow; API 35 fallback flow; deny read/write permissions and confirm app degrades to "choose another apply target"; no automatic prompt on screen entry.

- [ ] P1 - Backup/data-extraction inventory and secret/identity exclusions
  - Why: Aura excludes DataStore prefs and crash logs, but `allowBackup=true` leaves other state eligible by default, including the main Room DB and `aura_community_identity`.
  - Evidence: `AndroidManifest.xml`; `backup_rules.xml`; `data_extraction_rules.xml`; `CommunityIdentityProvider.kt`; Android Auto Backup docs.
  - Touches: backup XML, Room/favorites/export docs, identity prefs, API key storage docs, release checklist.
  - Acceptance: backup matrix declares include/exclude for Room DB, DataStore API keys, local identity UUID, weather lat/lon, crash logs, downloaded media, cached provider metadata, favorites, and collections; backup XML matches the matrix for Android 11 and Android 12+.
  - Verify: inspect APK backup XML; smoke-run app then list app data files and compare to matrix; restore simulation or manual D2D/cloud decision review.

- [ ] P1 - Weather location disclosure, retention, and clearing
  - Why: Weather effects use coarse location and send lat/lon to Open-Meteo, then store lat/lon in SharedPreferences for wallpaper rendering.
  - Evidence: `WeatherUpdateWorker.kt`; `SettingsScreen.kt`; Android approximate-location guidance; Play User Data location disclosure rules.
  - Touches: Settings weather toggle, `WeatherUpdateWorker`, `WeatherWallpaperService`, backup XML, privacy policy.
  - Acceptance: weather toggle explains approximate location and Open-Meteo call before permission request; app never requests `ACCESS_FINE_LOCATION` or `ACCESS_BACKGROUND_LOCATION` for weather; stored lat/lon are rounded or justified; disabling weather clears location/weather prefs and cancels work.
  - Verify: enable/deny/disable weather flows; confirm no background-location permission; inspect prefs after disable; network call contains expected rounded/coarse coordinates.

- [ ] P1 - Just-in-time permission disclosure and denial UX audit
  - Why: Aura requests sensitive capabilities across contacts, microphone recording, notifications, WRITE_SETTINGS, and location. Each needs a clear user action, rationale, decline path, and graceful fallback.
  - Evidence: manifest permissions; `SoundsScreen.kt` record flow; `SettingsScreen.kt` notification/location/settings flows; `ContactPickerScreen.kt`; Play prominent-disclosure guidance; Android runtime-permission docs.
  - Touches: permission launch sites, microcopy, Settings privacy screen, QA checklist.
  - Acceptance: no sensitive permission prompt fires before an explicit feature action; every denied permission leaves the rest of the app usable; permanent-denial states link to Android settings; release QA includes permission-denial screenshots.
  - Verify: revoke each dangerous/special permission and exercise feature flows; check no startup prompts; run manual screenshots for allow/deny/permanent-deny states.

- [ ] P2 - External automation consent, rate limit, and diagnostics
  - Why: The exported Tasker/MacroDroid receiver lets any app trigger wallpaper rotation broadcasts. The feature is useful but needs an opt-in boundary and observability.
  - Evidence: `TaskerActionReceiver.kt`; `AndroidManifest.xml` exported receiver; Play User Data and foreground-service user-awareness guidance.
  - Touches: Settings automation toggle, `TaskerActionReceiver`, `RotationTriggerService`, source diagnostics, README automation docs.
  - Acceptance: external broadcast actions are ignored until the user enables automation; repeated broadcasts are rate-limited; diagnostics show last external trigger time/package when available; docs list the public intent contract and risks.
  - Verify: broadcast ignored by default; enabled broadcast rotates once; burst broadcasts coalesce; diagnostics record external trigger state.

## Open Questions

- Should Aura publish a hosted privacy policy under GitHub Pages, the release README, or both?
- Should anonymous Firebase identity be enough for deletion requests, or should Google sign-in be required for self-service upload deletion?
- Should local favorites and Room state be backed up by default, or should backup be opt-in through explicit export/import only?
- Should the automation receiver expose a custom signature permission for advanced users, or is a Settings toggle plus rate limit sufficient?
