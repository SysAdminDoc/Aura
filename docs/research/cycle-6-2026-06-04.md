# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 6
**Date:** 2026-06-04
**Repo state:** `main`, `a60906f`, `v6.31.1-12-ga60906f`, `versionCode 112`

## Executive Summary

Cycle 6 focused on remote media ingestion, local file safety, cache lifecycle, and file-sharing boundaries. Aura already has meaningful hardening from prior implementation passes: scoped `MediaStore` writes, `IS_PENDING`, filename sanitization, several byte caps, temp-then-rename writes, and managed-path deletion checks. The remaining risk is unevenness. Some paths use streaming caps; others still use `body.bytes()` or raw `copyTo()`; some paths validate decoded media; others only validate file length.

Top findings:

- P0: Aura needs one media-ingestion policy and reusable capped-copy helper across every remote/local image, audio, video, and generated-media path.
- P1: `network_security_config.xml` still permits cleartext traffic for `ccmixter.org`. Android docs say broad cleartext should be avoided whenever possible; Aura should either remove the exception, proxy/mirror safely, or make ccMixter unavailable when HTTPS is not possible.
- P1: `FileProvider` exposes several cache/offline directories. FileProvider is the right mechanism, but the path allowlist should be narrowed so share flows export purpose-built files from `cache/share_out` instead of exposing long-lived caches.
- P1: Video wallpaper ingestion lacks a common byte cap and content validation path. `VideoWallpapersViewModel` writes Pexels/direct/YouTube fallback streams with raw `copyTo()`, and `VideoWallpaperStorage.prepareFromUri()` accepts user media into internal storage with only a minimal length check.
- P1: MIME and extension decisions are mostly URL/MIME-string based. Audio/image/video paths should validate decoded/probed content before applying, exporting, or persisting.
- P2: Cache budgets exist in silos (`AudioPreviewCache`, offline favorites, editor caches, live wallpaper files). A single storage budget/status policy would make Settings cleanup trustworthy.

## Current State

Local evidence reviewed:

- `DownloadManager.kt` streams wallpaper/audio downloads into `MediaStore` with advertised-size rejection and in-loop caps, uses `IS_PENDING`, sanitizes names, records download history, and avoids deleting unmanaged paths.
- `SoundApplier.kt` has a 64 MB cap for remote apply/download paths and writes audio to `MediaStore`, but local-file apply uses `FileInputStream.copyTo()` without a size/probe gate.
- `WallpaperApplier.kt` uses capped reads for URL/content/local wallpaper application and temp-then-rename for parallax image preparation.
- `OfflineFavoritesManager.kt` caps each favorite at 80 MB and total offline favorites at 512 MB, writes temp files, and prunes stale files.
- `VideoWallpaperStorage.kt` copies selected gallery media into `filesDir/live_wallpaper.*`; it validates existence and length over 1024 bytes but does not enforce a max byte cap or decode/probe the media type.
- `VideoWallpapersViewModel.kt` downloads Pexels/direct videos and YouTube fallback streams with raw `input.copyTo(output)` inside `prepareDownloadedVideo`.
- `VideoCropScreen.kt` caps remote video input at 256 MB, which is a stronger precedent for video paths.
- `ColorExtractor.kt`, `DualWallpaperService.kt`, `WallpaperCropViewModel.kt`, `WallpaperEditorViewModel.kt`, and `DailyWallpaperWorker.kt` still have `body.bytes()` call sites. Some check `Content-Length` first and then check `bytes.size`, but unadvertised/chunked bodies can still allocate before the post-read check.
- `AiWallpaperRepository.kt` writes generated image response bodies with raw `copyTo()`.
- `network_security_config.xml` permits cleartext traffic for `ccmixter.org`, while `AndroidManifest.xml` sets `android:usesCleartextTraffic="false"` at the application level.
- `file_paths.xml` exposes `shared/`, `offline_favorites/`, `cache/images/`, `cache/sounds/`, `cache/trimmed/`, `cache/audio_edit/`, and `cache/share_out/` through FileProvider.
- `CollectionExporter.kt` uses FileProvider for share-out JSON and sets `FLAG_GRANT_READ_URI_PERMISSION`; this is a good narrow-sharing precedent.

External evidence reviewed:

- Android network-security-config docs say apps can opt in to cleartext per destination, but a cleartext base config should be avoided whenever possible.
- Android FileProvider docs describe it as a secure way to share files through temporary `content://` URI grants instead of `file://` URIs.
- Android secure file-sharing docs caution that `setFlags()` on an intent is the secure way to grant temporary access and recommend FileProvider instead of `Uri.fromFile()`.
- Android storage docs say scoped storage gives apps access only to app-specific directories and media they created, improving user privacy.
- Android media-storage docs say apps can access their own MediaStore media without storage permissions, should be ready for I/O errors, and should not rely on the `DATA` column for newly created media.
- Android storage best-practice docs recommend app-specific storage for files other apps do not need and MediaStore for exported/user-facing media.

## Findings

### Media ingestion needs one contract

Aura has several hardened call sites, but not one enforceable contract. Remote images and sounds are mostly capped; remote video wallpaper apply and local video selection are less strict. Editor and color-extraction paths still have `body.bytes()` patterns that can allocate before a post-read cap when Content-Length is absent or wrong.

Planning implication: centralize media ingestion into a `MediaIngestionPolicy` and helper functions: allowed schemes, allowed hosts where relevant, max bytes by media class, stream caps, temp-then-rename, MIME/content probe, decode/probe validation, cancellation rethrow, and cleanup.

### Cleartext network exception should be retired or isolated

Aura has a scoped cleartext exception for `ccmixter.org`. That is better than app-wide cleartext, but still allows HTTP to one content provider. For a side-loaded media app, avoiding cleartext is part of trust and provenance.

Planning implication: prefer HTTPS-only ccMixter endpoints, remove ccMixter from active feeds if HTTPS cannot be guaranteed, or use a documented mirror/proxy with checksums and attribution. Keep a CI/static check that rejects new cleartext domains unless the provider policy doc approves them.

### FileProvider should expose only purpose-built share outputs

The current FileProvider allowlist includes offline favorites and several cache directories. FileProvider grants are temporary, but the broad path list means any future share intent bug could expose long-lived cached files. The safer pattern is already present in `CollectionExporter`: copy or render a share artifact to `cache/share_out`, grant read access, and clean it up.

Planning implication: narrow FileProvider paths to `share_out` and any specific recorder/export directory that truly needs external access. Generate share copies rather than sharing cache originals.

### Video wallpaper ingestion is the largest remaining size risk

Video wallpapers are naturally larger than images and sounds. `VideoCropScreen` already uses a 256 MB cap for remote input, but video wallpaper apply paths use raw copy. A server that omits Content-Length or streams unexpectedly large data can fill internal storage before `validatePreparedMotionFile()` runs.

Planning implication: align all video paths on a video max-byte policy, streaming cap, basic media probe, and friendly "too large/unsupported" user message.

### MIME type and extension are hints, not validation

Aura often guesses MIME type from URL extension or content resolver MIME. That is fine for display naming, but not enough before decoding/applying. The app should validate media by actually decoding image bounds, probing MediaMetadataRetriever/Media3 for video, and checking audio duration/container before writing public MediaStore rows or setting ringtones.

Planning implication: add content validation to the ingestion policy and tests with mismatched extensions, empty files, wrong MIME, huge dimensions, truncated media, and unsupported containers.

### Storage cleanup needs one budget story

Settings has a cache cleanup surface, but storage is split across Coil/Media3 cache, offline favorites, editor temp files, generated images, live wallpaper files, `share_out`, and MediaStore exports. Users need to know what is temporary, what persists after uninstall, and what "clear cache" deletes.

Planning implication: create a storage ledger and cleanup policy that lists every managed directory, budget, retention, backup behavior, and user-visible cleanup action.

## Roadmap Queue

- [ ] P0 - Unified media-ingestion policy and capped-copy helpers
  - Why: Aura downloads and imports images, audio, video, generated assets, and community media through several paths with different byte caps and validation behavior.
  - Evidence: hardened `DownloadManager`/`WallpaperApplier`/`OfflineFavoritesManager` paths; raw `copyTo()` in `VideoWallpapersViewModel`, `VideoWallpaperStorage`, `AiWallpaperRepository`; `body.bytes()` call sites in editor/color/dual/daily paths.
  - Touches: media ingestion helpers, download/apply/editor/video repositories, tests, `docs/security/media-ingestion.md`.
  - Acceptance: every remote/local media path declares allowed schemes, max bytes, temp-file behavior, cleanup, MIME/content validation, and user-facing error class; no direct `body.bytes()` or unbounded `copyTo()` remains on untrusted input.
  - Verify: unit tests for oversized advertised, oversized chunked, empty, truncated, wrong MIME, unsupported container, cancellation cleanup, and temp-file deletion.

- [ ] P1 - Remove or quarantine the ccMixter cleartext exception
  - Why: `network_security_config.xml` permits cleartext traffic for `ccmixter.org`; Android guidance says insecure cleartext config should be avoided whenever possible.
  - Evidence: `network_security_config.xml`; Android network-security-config docs; Cycle 3 provider-policy queue.
  - Touches: ccMixter repository, provider policy matrix, network security config, source fallback UI.
  - Acceptance: ccMixter uses HTTPS-only endpoints, is proxied/mirrored with provenance, or is disabled when HTTPS is unavailable; new cleartext domain additions require provider-policy approval.
  - Verify: static check for `cleartextTrafficPermitted="true"`; run ccMixter search over HTTPS; disabled-source fallback still leaves Sounds useful.

- [ ] P1 - Narrow FileProvider share surface
  - Why: FileProvider currently exposes offline favorites and multiple cache directories. Sharing should use purpose-built files in `cache/share_out` unless a flow explicitly requires another path.
  - Evidence: `file_paths.xml`; `CollectionExporter.kt` safe `share_out` precedent; Android FileProvider and secure file-sharing docs.
  - Touches: `file_paths.xml`, share/export flows, audio recorder export path, diagnostics sharing, cache cleanup.
  - Acceptance: FileProvider paths are minimized; share flows copy/render artifacts to `share_out`; old share files are pruned; no long-lived offline/cache originals are shared directly by default.
  - Verify: share collection/diagnostics/recording flows; inspect generated content URIs; denied direct sharing from removed paths; cleanup removes stale share artifacts.

- [ ] P1 - Video wallpaper size/probe hardening
  - Why: Pexels/direct/YouTube fallback video downloads and local video selection are the highest remaining media-size risk.
  - Evidence: raw `copyTo()` in `VideoWallpapersViewModel`; length-only validation in `VideoWallpaperStorage`; stronger 256 MB precedent in `VideoCropScreen`.
  - Touches: `VideoWallpapersViewModel`, `VideoWallpaperStorage`, `VideoCropScreen`, video apply/export UI, tests.
  - Acceptance: all video ingest paths stream-cap at a documented limit, reject too-small/too-large/truncated files, probe duration/dimensions/container before persisting, and surface actionable errors.
  - Verify: local huge file, chunked oversized HTTP, wrong-extension file, truncated video, GIF path, WebM/MKV/MP4 happy paths.

- [ ] P1 - MIME/content validation before public writes and apply actions
  - Why: URL extensions and content-resolver MIME strings are hints. Aura should validate actual content before writing MediaStore rows, setting system sounds, applying wallpapers, or caching favorites.
  - Evidence: MIME guessing in `DownloadManager`/`SoundApplier`; URL/MIME extension logic in `VideoWallpaperStorage`; Android media-storage docs.
  - Touches: image bounds decode, audio duration/container probe, video metadata probe, upload repositories, favorites/offline cache.
  - Acceptance: public writes and apply flows require content validation; mismatched extension/MIME files are rejected or normalized; thumbnails/previews do not trust provider-declared type alone.
  - Verify: tests for `.jpg` HTML body, `.mp3` image body, `.mp4` audio body, empty provider response, and oversized image dimensions.

- [ ] P2 - Managed storage ledger and cache cleanup policy
  - Why: Aura stores previews, offline favorites, edited audio, generated wallpapers, live wallpaper media, share artifacts, downloads, and provider metadata across several directories and MediaStore.
  - Evidence: `AudioPreviewCache` 48 MB, offline favorites 512 MB, `file_paths.xml`, Settings cache cleanup copy, backup rules from Cycle 4.
  - Touches: Settings storage screen, cache managers, backup/privacy docs, release QA.
  - Acceptance: `docs/privacy/storage-ledger.md` lists each directory/store, budget, retention, backup status, user cleanup action, and uninstall behavior; Settings cleanup copy matches actual behavior.
  - Verify: smoke-run all media flows, list files/directories, run clear cache, confirm retained/deleted state matches the ledger.

## Non-goals

- No implementation changes in this research pass.
- No source, tests, Gradle, workflow, resource, asset, or config edits.
- No claim that existing media paths are exploitable; this is a planning pass to close uneven file-safety controls.

## Open Questions

- Should video wallpaper downloads cap at 128 MB, 256 MB, or a duration/resolution-derived budget?
- Should ccMixter remain active if HTTPS is inconsistent, or should it move behind the Cycle 3 provider kill switch until fixed?
- Which share flows genuinely need FileProvider access beyond `cache/share_out`?
- Should MediaStore exports keep source provenance in display names/descriptions, or should provenance stay in Aura metadata only?
