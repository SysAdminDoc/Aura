# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 14
**Date:** 2026-06-04
**Repo state:** `main`, `2b3c3d8`, `versionCode 112`

## Executive Summary

Cycle 14 focused on background work, battery, and automation reliability. Aura has several background surfaces: periodic auto-wallpaper rotation, daily wallpaper notification, weather refresh, Aura Originals first-run download, unlock/screen-off trigger foreground service, Tasker/MacroDroid broadcast actions, video live-wallpaper battery caps, and startup cache cleanup.

The current implementation already uses WorkManager in many appropriate places, with battery/network constraints and exponential backoff. The planning gap is evidence and lifecycle correctness. Some work is periodic and system-deferrable, some is expedited and quota-limited, and one feature uses a long-lived `specialUse` foreground service reviewed by Play. Users and reviewers need a clear explanation of what is expected to run immediately, what may be delayed by Doze/App Standby, and what happens after reboot, notification denial, battery saver, or quota exhaustion.

Top findings:

- P0: `AndroidManifest.xml` declares `RECEIVE_BOOT_COMPLETED`, but local search found no `BOOT_COMPLETED` receiver. If no boot work is needed, the permission should be removed; if rotation triggers need boot restoration, the receiver and policy evidence are missing.
- P0: Background work has no central status/diagnostics surface for WorkManager states, last run times, constraint delays, failures, or expedited quota downgrade. Settings has source diagnostics and video battery dashboard, but not a background-jobs ledger.
- P1: `RotationTriggerService` uses `specialUse` FGS and dynamically registers unlock/screen-off receivers. It reconciles on app cold start and Settings toggles, but it does not survive reboot until the app runs again unless a boot receiver is added.
- P1: Unlock/screen-off and Tasker rotations enqueue expedited `AutoWallpaperWorker` with `RUN_AS_NON_EXPEDITED_WORK_REQUEST`. That is a good fallback, but it means "rotate now" can legally be delayed by quota, network, battery-not-low, Doze, and App Standby.
- P1: Auto-wallpaper periodic work uses `UPDATE` with user-selected constraints; daily wallpaper and weather use `KEEP`. This is plausible, but the roadmap needs a repeatable scheduling matrix so policy changes do not accidentally leave stale work requests.
- P2: Video live wallpapers have a battery-saver FPS cap and dashboard, but no formal battery/vitals regression script tying service visibility, battery percent, charging state, and user settings to measurable behavior.

## Current State

Local evidence reviewed:

- `AutoWallpaperWorker` reads scheduler/legacy preferences, fetches wallpapers from configured source, applies through `WallpaperApplier`, records history, retries on I/O/apply failure, and fails on other exceptions.
- `AutoWallpaperWorker.schedule()` reads charging/Wi-Fi/idle constraints from DataStore and schedules periodic work with a minimum 15-minute interval, battery-not-low, network connected or unmetered, optional charging, optional device idle, and exponential 15-minute backoff. It uses `ExistingPeriodicWorkPolicy.UPDATE`.
- `SettingsViewModel` reschedules auto-wallpaper work when the user changes interval or charging/Wi-Fi/idle constraints.
- `DailyWallpaperWorker` runs every 24 hours with an 8-hour initial delay, connected-network constraint, exponential backoff, and `ExistingPeriodicWorkPolicy.KEEP`. It exits successfully if `POST_NOTIFICATIONS` is not granted.
- `WeatherUpdateWorker` runs every 30 minutes with connected-network constraint, exponential backoff, and `ExistingPeriodicWorkPolicy.KEEP`. It skips if no location permission or last-known location exists.
- `AuraOriginalsDownloader.enqueue()` runs on app startup, requires unmetered network, uses expedited one-time work with `RUN_AS_NON_EXPEDITED_WORK_REQUEST`, exponential backoff, and `ExistingWorkPolicy.KEEP`.
- `RotationTriggerService` is exported false, uses foreground-service type `specialUse`, declares subtype `wallpaper_rotation_triggers`, dynamically registers `ACTION_USER_PRESENT` and `ACTION_SCREEN_OFF`, and enqueues a coalesced expedited one-shot `AutoWallpaperWorker` named `rotation_trigger_oneshot`.
- `TaskerActionReceiver` is exported true and calls `RotationTriggerService.enqueueRotation(context)` for `ROTATE_NOW` and `SHUFFLE_NOW`.
- `FreeVibeApp.onCreate()` reconciles rotation triggers, enqueues Aura Originals download, initializes yt-dlp/FFmpeg, evicts stale caches, and warms community identity.
- `AndroidManifest.xml` declares `RECEIVE_BOOT_COMPLETED`, but this pass found no receiver with a `BOOT_COMPLETED` action.
- No `AlarmManager`, `SCHEDULE_EXACT_ALARM`, or `USE_EXACT_ALARM` code path was found; Cycle 11 separately flagged dormant `SET_ALARM`.
- `VideoWallpaperService` and `SettingsScreen` compute battery snapshots, cap effective FPS under low battery/auto-saver conditions, and expose a battery dashboard.

External evidence reviewed:

- Android WorkManager docs say periodic work's interval is the minimum time between runs; exact execution depends on constraints and system optimizations, and the minimum repeat interval is 15 minutes.
- WorkManager constraints can defer or skip periodic work when network, battery-not-low, charging, device-idle, or storage-not-low conditions are not satisfied.
- WorkManager expedited work is for user-important, short, immediate tasks, but it is quota-limited by standby bucket/process importance. If quota is exhausted, `RUN_AS_NON_EXPEDITED_WORK_REQUEST` runs as ordinary work.
- Android Doze and App Standby defer background CPU, network, jobs, syncs, and standard alarms until maintenance windows, and developers should test apps in those modes.
- Android alarm docs say most scheduled background work should use inexact alarms or WorkManager; exact alarms are reserved for core precise-alarm functionality such as alarm clocks or calendars.
- Android foreground-service docs require `specialUse` subtype metadata and say Play reviews the free-form use case. Play foreground-service declaration docs require descriptions, interruption impact, deferral impact, and demo videos for each FGS type.

## Findings

### Boot behavior needs a decision

WorkManager can persist periodic jobs across process death and reboot, so `RECEIVE_BOOT_COMPLETED` might not be needed for auto-wallpaper, daily wallpaper, weather, or Aura Originals. Rotation triggers are different: the foreground service registers dynamic receivers only while running. After reboot, those receivers will not exist until Aura starts and calls `reconcileRotationTriggers()`.

Planning implication: either remove `RECEIVE_BOOT_COMPLETED` and document that rotation triggers resume after the user opens Aura, or add a boot receiver that only restarts `RotationTriggerService` when the user opted in and the Play FGS declaration explains why.

### Users need background-work observability

Aura has source diagnostics and video battery state, but background jobs are otherwise invisible. When WorkManager defers work for constraints, Doze, App Standby, unmetered network, quota, or notification denial, users will experience it as "auto-rotate did not run" unless Settings can show last run, next eligibility, current constraints, and recent failures.

Planning implication: add a background-jobs diagnostics card backed by `WorkManager.getWorkInfosForUniqueWork*` and local worker result receipts. It should cover auto wallpaper, daily wallpaper, weather, Aura Originals, and rotation trigger one-shots.

### Expedited does not mean guaranteed immediate

Unlock/screen-off, Tasker, and Aura Originals all use expedited work with downgrade on quota exhaustion. That is usually correct, but the UI and docs should not promise immediate execution. The existing Tasker receiver comment already says constraints may defer rotation; Settings and diagnostics should make that visible.

Planning implication: treat "rotate now" as "enqueue a rotation attempt that respects constraints." If the user expects instant rotation, add a foreground/manual path from visible UI that can bypass some background constraints safely or at least report why it deferred.

### Unique-work policies need a scheduling matrix

`UPDATE` for auto-wallpaper is useful because interval and constraints change. `KEEP` for daily/weather/Aura Originals avoids duplicate work. However, without a matrix, future changes can silently leave old requests in place. For example, changing weather interval, adding unmetered-only weather, or changing Aura Originals manifest version may need `UPDATE` or a versioned work name.

Planning implication: document each unique work name, policy, interval, constraints, retry behavior, schedule trigger, cancellation trigger, and whether changes require update/cancel/re-enqueue.

### Battery claims need measurable release evidence

Video battery dashboard and FPS caps are useful, but release planning should measure the behavior. Live wallpapers, background rotations, and downloads can all affect Android vitals categories such as excessive battery usage, wakeups, background network use, and foreground-service time.

Planning implication: add a battery/background QA script with `adb shell dumpsys jobscheduler`, `dumpsys batterystats`, WorkManager inspection, notification-permission denial, Doze/App Standby simulation, and video wallpaper battery-saver scenarios.

6. P2 - Battery/vitals regression lab for live wallpapers and schedulers.

## Verification Targets

- Fresh install, process death, reboot, app standby buckets, Doze, battery saver, notification denial, and no-network states are tested against every background feature.
- `RECEIVE_BOOT_COMPLETED` is either removed or backed by a receiver that respects user opt-in and Play FGS declaration evidence.
- Settings can show current WorkManager state, last success/failure, constraints, and user-actionable deferral reasons.
- Expedited rotation tests cover quota downgrade and coalescing under repeated unlock/Tasker triggers.
- Battery/vitals script records foreground-service time, background network, job counts, and video FPS caps.
