# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 5
**Date:** 2026-06-04
**Repo state:** `main`, `039cbdf`, `v6.31.1-11-g039cbdf`, `versionCode 112`

## Executive Summary

Cycle 5 focused on accessibility, localization, and inclusive QA. Aura is visually rich and interaction-dense: wallpaper grids, video previews, audio playback controls, live wallpaper settings, custom scrubbing/editing, uploads, diagnostics, and widgets. Compose and Material components provide useful defaults, but Aura has enough custom surfaces that accessibility cannot be left to defaults.

Top findings:

- P0: Aura needs an accessibility release gate that combines automated Compose accessibility checks, Accessibility Scanner recording, and manual TalkBack/Switch Access/large-font passes over the core flows.
- P1: The UI is still mostly hardcoded English. A quick source count found roughly 300 hardcoded visible-string patterns, only 6 `stringResource`/`R.string`/`@string` references, and only `res/values` with no locale-specific `values-*` directories.
- P1: Compose semantics need a custom-component pass for waveform/progress controls, wallpaper/video cards, source badges, vote/hide actions, settings toggles, and editor controls. Search found no `stateDescription`, `customActions`, `onClick(label=...)`, or `heading()` usage in app/test sources.
- P1: Android 14 supports 200% nonlinear font scaling; Aura needs a large-font and display-size audit because many screens use dense rows/cards/chips and short icon buttons.
- P2: Widgets and live-wallpaper picker metadata have some string resources, but most app and toast copy remains unlocalized. Per-app language support should be planned after string extraction, not before.

## Current State

Local evidence reviewed:

- Search found only `app/src/main/res/values`; there are no translated `values-*` resource folders.
- Search found 6 `stringResource`/`R.string`/`@string` matches across Kotlin/XML resources. Most visible Compose copy is inline.
- Search found about 300 hardcoded visible-string patterns in Kotlin, including `Text("...")`, dialog titles/labels/descriptions, and Toast strings.
- Search found about 101 decorative/null content-description patterns. Some are appropriate for decorative icons, but this needs auditing because clickable/custom controls cannot be treated as decorative.
- Search found no `enableAccessibilityChecks`, `ui-test-junit4-accessibility`, `stateDescription`, `customActions`, `onClick(label=...)`, or `heading()` usage in app/test/baselineprofile sources.
- `SoundsScreen.kt` has a good precedent: the play button uses a dynamic semantics content description for play/pause state.
- `FreeVibeWidget.kt`, live-wallpaper XML files, and a few launcher/widget resources already use string resources, so extraction has a small starting point.
- `ROADMAP.md` already has U-11 localization and U-13 accessibility concepts, but they are broad and not tied to acceptance tests or release gates.

External evidence reviewed:

- Compose semantics docs say semantics provide accessibility/testing context and can define state descriptions and custom actions for components.
- Compose API-default docs say images/icons need textual descriptions because the framework cannot infer what graphics mean, and custom click labels improve TalkBack action hints.
- Compose accessibility-testing docs say Compose 1.8+ can use the Accessibility Test Framework through `ui-test-junit4-accessibility` and `enableAccessibilityChecks()`.
- Android Accessibility Scanner checks content labels, touch target size, clickable items, and text/image contrast; Google explicitly says it is not a replacement for manual testing.
- Android touch-target guidance recommends at least 48 dp by 48 dp touch targets, 8 dp separation where possible, and `Modifier.sizeIn` for dynamically sized Compose controls.
- Android color-contrast guidance references 4.5:1 for small text and 3:1 for large text/iconography, with Scanner as a manual/on-device check.
- Android 14 docs say font scaling can reach 200% and apps should test with maximum font size enabled.
- Android per-app language docs say Android 13 provides central per-app language preferences and AGP can generate locale config, but production apps should not enable locales until all included locales are ready.

## Findings

### Accessibility needs a release gate, not a best-effort sweep

Aura's primary workflows are not simple forms. Users browse dense cards, preview audio, apply wallpapers, manipulate crops/timelines, inspect source metadata, upload community media, and toggle background behaviors. Automated checks will catch missing labels, small touch targets, and contrast issues, but TalkBack order, state announcements, editor affordances, and live-wallpaper preview behavior need manual passes.

Planning implication: create a release-blocking accessibility checklist and wire the Compose accessibility test artifact into key screen tests. Start with highest-use flows: Wallpapers, Videos, Sounds, Favorites, Settings, Sound Detail, Wallpaper Detail/Crop, Video Crop, Upload, Diagnostics, Widget, and live-wallpaper picker.

### Localization cannot start until strings are extracted

The current codebase is English-hardcoded. Android's per-app language support is useful, but enabling locale config before real translations would expose empty or partial languages. The right first step is extracting visible copy to resources or a Compose string wrapper, then choosing translation infrastructure and initial locales.

Planning implication: add a string-extraction milestone with a no-new-hardcoded-strings check, then enable generated locale config only after translated resource sets are complete enough to publish.

### Custom controls need explicit semantics

Aura has audio/video/wallpaper controls where visual state carries meaning: play/pause, progress/waveforms, vote status, source/quality badges, filter chips, timeline range selection, crop position, wallpaper apply targets, live weather/rotation toggles, and diagnostics status. Compose Material covers many standard controls, but custom components need state descriptions, click labels, roles, headings, progress semantics, and custom accessibility actions.

Planning implication: define a semantics matrix by component type and make screen tests assert the important labels/states.

### Large font and high-contrast behavior is unproven

Android 14's 200% font scaling makes truncation and clipped controls more likely in dense dashboard-style screens. Aura's compact buttons, filter chips, metadata rows, card overlays, bottom sheets, and editor timelines need a maximum-font audit.

Planning implication: add screenshots or manual evidence at font scale 200%, display size high, dark/light themes, and high contrast/outline text where supported.

### Widgets and live-wallpaper surfaces need their own accessibility plan

The Glance widget has string resources and content descriptions, but widget actions, live-wallpaper picker labels/descriptions, and wallpaper service overlays are outside the main Compose tree. They need separate coverage in the accessibility checklist.

Planning implication: include launcher widget, keyguard widget placement, and Android live-wallpaper picker previews in the same a11y/localization gate.

## Roadmap Queue

- [ ] P0 - Accessibility release gate for core Aura flows
  - Why: Aura has dense custom Compose surfaces and no automated accessibility-check wiring. Accessibility Scanner and Compose tests can catch regressions before release, while TalkBack/manual passes catch interaction-order and state-announcement issues.
  - Evidence: no `enableAccessibilityChecks`/`ui-test-junit4-accessibility` found; Compose accessibility-testing docs; Accessibility Scanner docs; Aura's image/audio/video/settings/editor/widget surfaces.
  - Touches: UI test dependencies, screen tests, QA checklist, release checklist, `docs/qa/accessibility.md`.
  - Acceptance: key Compose screen tests enable accessibility checks; manual checklist covers TalkBack, Switch Access/keyboard-like navigation, 200% font, high contrast, dark/light themes, widget, and live-wallpaper picker; release notes require passing or explicitly waiving the gate.
  - Verify: run focused accessibility UI tests; capture Accessibility Scanner recording for primary flows; manual TalkBack pass for Wallpapers/Videos/Sounds/Settings/detail/editor flows.

- [ ] P1 - Extract visible strings and plan first localization batch
  - Why: Aura is mostly hardcoded English today, with about 300 hardcoded visible-string patterns and only the base `values` resource directory.
  - Evidence: `rg` counts in Cycle 5 research; Android per-app language docs; existing U-11 roadmap item.
  - Touches: Compose screens, resources, widgets, live-wallpaper metadata, CI lint/search check, Weblate/Crowdin decision.
  - Acceptance: visible strings live in resources or a central string abstraction; no new hardcoded user-visible strings in Kotlin except test/debug/source-provider literals; first-locale list and translation workflow documented; generated locale config stays disabled until translations are complete enough to publish.
  - Verify: hardcoded-string scanner; resource build; pseudo-localization/manual long-string pass; RTL smoke test with Arabic/Hebrew pseudo-content.

- [ ] P1 - Custom component semantics matrix
  - Why: Wallpaper/video cards, audio preview buttons, waveform/progress displays, vote/hide actions, filter chips, source/license badges, crop/timeline editors, and settings toggles need explicit labels, state descriptions, and custom actions.
  - Evidence: no `stateDescription`, `customActions`, `onClick(label=...)`, or `heading()` found; Compose semantics/API-default docs.
  - Touches: shared components, Wallpapers/Videos/Sounds screens, Sound Detail, editor screens, Settings, widget actions.
  - Acceptance: each reusable component declares required semantics; interactive icons have action labels; progress/waveform/timeline controls expose progress/range state; repeated card secondary actions move to custom actions where TalkBack traversal would be noisy.
  - Verify: Compose semantics assertions; TalkBack announces play/pause/vote/apply/crop states correctly; decorative icons remain hidden from screen readers.

- [ ] P1 - 200% font, display-size, and contrast audit
  - Why: Android 14 supports 200% nonlinear font scaling. Aura's dense chips, cards, overlays, bottom sheets, and editor timelines may clip or overlap at large fonts.
  - Evidence: Android 14 nonlinear font-scaling docs; Android touch-target and color-contrast guidance; Aura compact UI/search findings.
  - Touches: typography/layout constraints, chip/card rows, bottom sheets, dialogs, editor controls, Material color roles, screenshot QA.
  - Acceptance: primary flows remain usable at 200% font and large display size; controls keep at least 48 dp touch targets where feasible; critical text/icon contrast passes scanner thresholds; no text overlaps controls.
  - Verify: manual screenshots at 200% font; Accessibility Scanner contrast/touch-target results; dark/light/high-contrast pass.

- [ ] P2 - Widget and live-wallpaper accessibility/localization coverage
  - Why: Widgets and live-wallpaper picker metadata are not covered by normal Compose screen traversal but are visible entry points for Aura.
  - Evidence: `FreeVibeWidget.kt`, `freevibe_widget_info.xml`, live-wallpaper XML metadata; Android Accessibility Scanner manual workflow.
  - Touches: Glance widget copy/actions, keyguard widget state, live-wallpaper labels/descriptions, launcher/picker QA.
  - Acceptance: widget actions have localized labels and useful spoken descriptions; live-wallpaper picker labels/descriptions are localized; keyguard widget and launcher widget remain usable at large font/display settings.
  - Verify: add widget, keyguard placement where available, trigger widget actions, inspect picker labels, run scanner/manual TalkBack pass.

## Non-goals

- No implementation changes in this research pass.
- No source, tests, Gradle, workflow, resource, or asset edits.
- No final locale selection; this pass only defines the prerequisite extraction and QA work.

## Open Questions

- Should Aura use Android string resources directly everywhere, or introduce a small Compose string wrapper for dynamic provider/source names?
- Which first locales should be accepted into a release: community-requested languages, top GitHub/Obtainium geographies, or maintainer-reviewed languages only?
- Should accessibility scans become a release artifact alongside baseline-performance artifacts?
- Should live-wallpaper/editor controls expose alternate non-gesture controls for every operation before advanced visual effects expand further?
