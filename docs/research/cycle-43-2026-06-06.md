# Cycle 43 Research: Pixabay Photo Request Cache And Backoff

## Goal

Begin closing the Pixabay policy gap by enforcing a 24-hour request-cache path
and 429 backoff for Pixabay photo API calls.

## Source Evidence

- [Pixabay API documentation](https://pixabay.com/api/docs/) states that
  requests must be cached for 24 hours.
- The same documentation describes rate-limit headers including
  `X-RateLimit-Reset` and 429 behavior for exceeded API limits.

## Local Evidence

- `WallpaperCacheManager` had source-specific TTLs, but no Pixabay TTL; Pixabay
  fell through to the default six-hour wallpaper metadata TTL.
- `WallpaperRepository.getPixabay()` always called the API when enabled and a
  key was available, then only used stale cache as an error fallback.
- `VideoWallpapersViewModel` calls `PixabayApi.searchVideos()` directly and has
  no durable video metadata cache. That path remains a follow-up.
- `ProviderDisclosure.kt` and `docs/legal/provider-runtime-controls.md` already
  kept Pixabay `Partial` because provider TTL and rate-limit behavior were not
  enforced.

## Decision

Implement the durable photo-side guard first because it can reuse the existing
Room-backed wallpaper metadata cache. Keep Pixabay marked `Partial` until video
metadata receives equivalent caching/backoff.

## Implementation Notes

- `WallpaperCacheManager` now gives `ContentSource.PIXABAY` a 24-hour fresh-cache
  TTL.
- `WallpaperRepository.getPixabay()` now checks fresh cache before calling the
  API, so repeated Discover/search/style-biased calls inside the TTL avoid
  duplicate requests.
- Pixabay 429 responses now parse `Retry-After` first, then
  `X-RateLimit-Reset`, and set an in-session backoff window.
- During backoff, `getPixabay()` returns stale cached rows when available or an
  empty source result when no cache exists, avoiding retry loops.

## Verification Plan

- Focused repository test proves fresh Pixabay cache is returned before any API
  call.
- Focused parser test proves retry headers produce the expected backoff.
- Provider disclosure test verifies the remaining partial follow-up is explicit.
- Release-compliance Python checks remain unchanged and should still pass.
