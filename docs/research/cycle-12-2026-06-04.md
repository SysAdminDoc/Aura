# Project Research and Feature Plan

**Project:** Aura (`com.freevibe`)
**Cycle:** 12
**Date:** 2026-06-04
**Repo state:** `main`, `bacf713`, `versionCode 112`

## Executive Summary

Cycle 12 focused on accountless community identity, deletion, and retention. Aura's store listing says "no account required," but the app currently warms community identity on startup, signs in anonymously with Firebase when available, and uses that UID for community uploads, votes, follows, creator dashboards, and moderation/admin checks. That is a reasonable product model, but it needs explicit user control and a deletion path.

Google Play's app-account deletion guidance is triggered when an app enables account creation. Even if Aura frames this as anonymous community identity rather than a password account, the safest release posture is to treat Firebase anonymous identities as app-account-like data when they protect user-generated content. Play also requires Data safety deletion answers, and all data disclosed as collected is in scope for deletion practices.

Top findings:

- P0: `FreeVibeApp.warmCommunityIdentity()` calls `CommunityIdentityProvider.ensureSignedIn()` on startup, so a Firebase anonymous account can be created before the user uploads, votes, follows, or opens the creator profile.
- P0: No app-side account/community-data deletion path was found. Local search did not surface `deleteAccount`, Firebase `currentUser.delete()`, or a user-facing deletion UI for uploads, votes, follows, profiles, or identity reset.
- P0: Community data spans multiple backends: Firebase Auth anonymous users, RTDB `community_sounds`, `community_wallpapers`, `votes`, legacy `voters`, `creator_profiles`, `creator_follows`, `collection_shares`, and Firebase Storage objects.
- P1: Upload metadata stores public download URLs but not an explicit `storagePath` deletion handle or per-owner upload index, making reliable owner deletion and admin/web deletion harder than it needs to be.
- P1: `CommunityIdentityProvider.knownIdentityIds()` includes Firebase UID, fallback UUID, and legacy `Settings.Secure.ANDROID_ID`. This helps migrate votes, but it expands the identity surface that privacy/deletion docs need to cover.
- P1: Firebase anonymous-account automatic cleanup can delete old anonymous Auth users only when Identity Platform cleanup is enabled, but it does not by itself delete RTDB/Storage content written under that UID.

- `CreatorProfileRepository.getDashboard()` aggregates public community uploads and local favorites, using `knownIdentityIds()` to treat Firebase UID/fallback/legacy IDs as the current creator.
- `database.rules.json` allows public reads for votes, moderation, uploads, profiles, and collection shares; owner/admin writes for uploads, profiles, and collection shares; authenticated follower writes for `creator_follows/{followerUid}`; and admin-only moderation writes.
- No tracked `storage.rules`, `firebase.json`, `.firebaserc`, or Firebase rules test harness was found in Cycle 9, and no new matching files surfaced in this pass.
- Settings exposes "Creator profile" with subtitle "Uploads, votes, follows, and leaderboard"; no nearby "delete community data", "reset identity", or privacy/account controls were found.
- `docs/privacy` is still absent; Cycle 8 already queued a public privacy policy and in-app privacy link.

External evidence reviewed:

- Google Play's account deletion guidance says developers must answer Data safety deletion questions, and apps that enable account creation must provide an in-app path to delete app accounts and associated data plus a web resource for users who cannot access the app.
- The same guidance says all user data indicated as collected in the Data safety section is in scope unless retention exceptions are clearly disclosed.
- Firebase anonymous-auth docs describe anonymous accounts as temporary accounts for data protected by security rules. They also note optional automatic cleanup for anonymous accounts older than 30 days when Firebase Authentication with Identity Platform is enabled.
- Firebase Auth Android docs provide `FirebaseUser.delete()` for deleting the signed-in user, with recent sign-in requirements.
- Firebase Realtime Database Android docs say `removeValue()` deletes data at a reference, and setting a child to `null` through `updateChildren()` can delete multiple children atomically.
- Firebase Storage Android docs support `StorageReference.delete()` for uploaded files and warn that deletes can fail when the file is missing or the caller lacks permission.

## Findings

### Anonymous community identity is currently created too early

The community identity warm-up happens during app startup, not only when the user takes a community action. That makes the "no account required" claim more fragile: a user who never uploads, votes, follows, or opens creator profile may still get a Firebase anonymous account. It also broadens the deletion obligation because Auth state exists before the user has opted into community participation.

Planning implication: make public community browsing read-only without Auth, and create anonymous identity only when the user performs a write action or explicitly opens a creator/community profile that needs identity. Admin-claim refresh can move behind that same lazy identity boundary or a separate admin/dev-only path.

### Deleting an anonymous identity is not enough

Firebase Auth can delete the current user, but Aura's visible community data lives in RTDB and Storage. Deleting only the Auth user would orphan public uploads, votes, follows, profile data, and share tokens under an unresolvable UID. Conversely, deleting only RTDB metadata would leave Storage files reachable if URLs remain cached or indexed.

Planning implication: deletion must be orchestrated across Auth, RTDB, Storage, local prefs, and local caches. A successful deletion should either delete public content or deliberately anonymize/retain specific records with a documented reason and visible user choice.

### The current data model is not deletion-friendly

Sound and wallpaper uploads write Storage paths based on UID, but RTDB metadata stores public download URLs rather than a canonical `storagePath`. There is no per-owner upload index such as `owner_uploads/{uid}/{uploadId}`. That means deletion needs broad scans of public collections and URL-to-storage resolution, which is brittle for app-side deletion and web/admin requests.

Planning implication: future uploads should store deletion handles and owner indexes. Existing uploads need a backfill or admin script that reconstructs paths from URL/object metadata before any deletion guarantee is published.

### Votes and follows need their own deletion semantics

Vote markers are deliberately used to prevent duplicate voting. If deletion removes voter markers, users may be able to vote again after recreating identity; if deletion keeps hashed/tombstoned markers, the policy must disclose retention. Follows are simpler for outbound records, but inbound references to a deleted creator can remain in other users' `creator_follows`.

Planning implication: define separate deletion semantics for user-generated content, vote integrity, follower graph, moderation/audit records, and abuse-prevention tombstones. Do not hide those policy choices inside a generic "delete account" button.

### A web deletion request path needs backend/admin tooling

Play expects a web resource so users can request deletion after uninstalling. Since Aura is an Android app with anonymous identities, a web request cannot rely on the app's current Firebase session. It needs either a support workflow that verifies identity through an in-app export/deletion code, or a backend/admin process that can map user-provided identifiers to backend records without exposing other users' data.

Planning implication: ship an in-app "community data receipt" that shows the user their UID suffix, auth type, uploaded item IDs, and a deletion request code. Pair it with a web/email request flow and an admin deletion runbook.

## Verification Targets

- Fresh install can browse public community content without creating a Firebase anonymous Auth user.
- Upload, vote, follow, and creator-profile actions create identity only after explicit user action and show the current auth label.
- In-app deletion removes or anonymizes all scoped RTDB records, deletes Storage objects, deletes the Firebase Auth user when possible, clears `aura_community_identity`, and refreshes UI to signed-out/local state.
- Web/admin deletion test seed covers a user with sound uploads, wallpaper uploads, votes, follows, profile data, collection shares, and moderated content.
- Data safety and privacy docs clearly state what is deleted, what may be retained, why, and for how long.
